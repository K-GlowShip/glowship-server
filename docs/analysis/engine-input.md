# 실행 하나의 엔진 입력과 조회 도구 T1~T5·T8

- 대상: `app/modules/delay_analysis/infrastructure/engine/engine_input.py`(엔진 입력), `engine_operating_rules.py`(운영 기준 검사, 같은 폴더), `app/modules/delay_analysis/application/agent/tools/lookup_tools.py`(조회 도구), 시험 `tests/modules/delay_analysis/test_engine_input.py`
- 티켓: GLOW-125 2부 (상위 GLOW-20). 1부는 엔진 입력 저장소(`engine-input-store.md`, PR #36). 운영 기준 검사는 GLOW-100(이슈 #61, 4절 8번)
- 계약: `docs/agent-flow/tool-contracts.md` 3절(조회 도구 출력), 도구 호출 인터페이스(GLOW-129 `agent-tool-interface.md`) 결정 1~3
- 쓰는 곳: 그래프 준비 노드(GLOW-129)가 실행마다 한 번 만들어 `ToolContext.engine`에 넣고, 도구 T1~T8·설명 생성이 읽습니다

## 1. 왜 이렇게 나눴나
- 엔진은 `pipeline.analyze(snap)` **한 번**으로 예측 층·주문 층·영향 집합·결과 분류·대응안·판정 서명·의존 범위를 함께 계산합니다(`pipeline.py` 64~79행). 판정 서명에는 대응안 결과까지 들어갑니다.
- 도구마다 따로 계산하면 도구 출력과 판정 서명이 다른 계산에서 나올 수 있습니다. 그래서 **실행마다 엔진 입력(스냅샷 + 계산 결과)을 한 번 만들고, 도구는 거기서 옮기기만** 합니다.
- 도구는 DB를 다시 읽지 않습니다. 입력 순번 뒤에 바뀐 값이 섞이지 않고, 몇 번 불러도 같은 값입니다.

## 2. 흐름 (엔진 하네스 `run_s1_s5.analyze_run`과 같은 순서)
| 단계 | 함수 | 결과 |
| --- | --- | --- |
| 1. NO_DELAY 판정 | `judge_no_delay(session, run)` | E ≤ P면 `NoDelay`(판정 서명·SHA-256) → `save_no_delay`. 저장소를 읽지 않습니다(가벼운 조회 두 개) |
| 2. 엔진 입력 | `build_engine_input(session, run)` | 저장소(#36) → `snapshot.build` → 운영 기준 검사(4절 8번) → `pipeline.analyze`. 입력 검증 실패(엔진 `Hold`, 계산이 지원하지 않는 운영 기준)는 `EngineHold(code, message)`로 돌려줍니다(예외 아님) → 실행 ON_HOLD(VALIDATING) |
| 3. 도구 | `lookup_tools.get_*`(T1~T5·T8) | `ctx.engine.snap`을 계약 출력 모델로 옮김 |
| 4. 판정 서명 | `decision_of(engine)` | `EngineDecision`(상태·결과 분류·`dependency_scope`·`decision_signature`·`decision_signature_sha256`). 결과 저장(#38)의 같은 이름 칸에 그대로 넣습니다. 복사본을 돌려줍니다 |

- 저장소·입력 순번이 맞지 않거나 실행의 지연 이벤트·트리거 스냅샷을 못 찾으면 `EngineInputError`·`LookupError`를 올립니다. 이것은 보류가 아니라 시스템 문제입니다. 지연 이벤트를 못 찾는 흔한 원인은 RLS입니다(앱 역할 세션, ACTIVE가 아닌 고객사). 그래서 오류 메시지가 저장소(`_check_not_silently_empty`)와 같이 두 가지를 확인하라고 안내합니다.

## 3. 실행 행에서 엔진 입력 값을 정하는 규칙 (#36 정답 대조와 같음)
| 엔진 값 | 정하는 법 |
| --- | --- |
| 입력 확정 시각 `confirm_t` | `engine_timestamp(run.started_at)`(UTC, 초 아래 버림) |
| 기준일 D | `resolve_base_date(store, company_id, confirm_t)`: **min(실행 날짜, 최신 재고일 + 1, 성공한 주문 수집이 다룬 마지막 접수일 + 1)**(이슈 #51 사용자 결정, 4절 7번). 실행 날짜 = `confirm_t`의 날짜(`run_code` 날짜와 같음). 결과는 `EngineInput.base_date`와 근거 `EngineInput.base_date_resolution`(`BaseDateResolution`: D·실행 날짜·재고 한도·주문 한도·늦은 원천 `late_sources`) |
| 지연 선적 | `delay_events.shipment_id` |
| 단계·예상 입고일 E | 실행의 트리거 일정 스냅샷(`trigger_shipment_schedule_snapshot_id`). **트리거가 없으면(재분석)** 엔진처럼 입력 확정 시각까지의 최신 관측(`store.snapshot_at`). 계약 3.1절·9절 Q16과 같음 |
| 계획 입고일 P | `shipments.planned_3pl_inbound_date` |
| 행사 일정 | 엔진 폴더 `glowship_engine/config/event_calendar_2026h1_v1.json`(하네스 `run_s1_s5.CAL`과 같은 파일, 해시는 엔진 매니페스트가 고정) |

- **전제(11-06, #36 리뷰 후속):** `run.started_at`은 **수집과 같은 시각 기준**이어야 합니다. #40으로 수집 시각은 가상 시각(기본 2026-07-02부터 하루씩)이 됐는데, 실행 생성(GLOW-99 `create_analysis_run`)은 아직 `clock_timestamp()`(실제 시각)입니다. 실제 시각으로 만든 실행을 넘기면 D가 11월이 되어 28일 ORDER 수집이 없다며 **모든 실행이 보류**됩니다(재현: A_BEAUTY 실행을 `2026-11-06T01:43Z`로 넘기면 `REQUIRED_DATA_INVALID "ORDER 수집 결측일 [2026-10-09 …]"`, 마지막 수집 시각 + 1분으로 넘기면 `NO_RISK`). 엔진 하네스는 AUTO 실행을 수집한 날 `00:05Z`, 재분석을 사용자 요청 시각으로 만들어 늘 수집과 같은 날입니다. 고치는 곳은 실행 생성·자동 시작이고, 이 문서의 규칙(`started_at` → D)은 serviceflow 337행과 같아 그대로 둡니다. **11-07 바뀜:** D는 이제 4절 7번 규칙으로 정합니다. 그날 자료가 아직 입력에 없는 실행(하루 차이)은 보류되지 않고 마지막 자료 날로 계산합니다. 시각 기준이 몇 달씩 어긋나는 문제(위 11월 예)는 그대로라 위 고칠 곳도 그대로입니다.
- NO_DELAY 판정은 저장소 없이 SQL로 E를 읽습니다. 트리거가 없을 때의 "최신 관측"은 엔진 `snapshot_at`과 같게 고릅니다: 입력 순번까지 적재된 관측 중 `observed_at`(초 아래 버림) ≤ `confirm_t`인 마지막 것, 같은 초면 읽은 순서(`ctid`)의 마지막.

## 6. 작업 중 실패와 원인
- **트리거 값을 엔진에 넘기지 않아도 정답 대조 21건이 통과했습니다.** overlay 데이터는 모든 AUTO 실행의 트리거 스냅샷이 입력 확정 시각의 최신 관측과 같아서, 엔진이 스스로 고른 값과 차이가 나지 않습니다. 데이터 대조로는 이 규칙을 확인할 수 없음을 변이 시험으로 알았습니다 → 엔진 모듈을 대역으로 바꿔 엔진에 넘기는 값을 직접 보는 시험을 더했습니다.
- 계약 문서 3절에 `UNEXPECTED_TOOL_ERROR`를 백틱으로 적었다가 계약 시험(`test_doc_codes_are_known`)이 "모르는 코드"로 잡았습니다. 계약 문서의 백틱 대문자 값은 서버 열거형(`analysis_enums`, DDL CHECK 값)·사전 판정 값·시험의 예외 목록과 대조됩니다 → 실패 코드 이름을 빼고 문장으로 적었습니다.
- 3.5절 `allocation_state` 형식을 표로 적으면 계약 시험이 표의 필드를 모델과 대조합니다(모델은 아직 `list[dict]`). 그래서 목록으로 적었습니다.
- 단위 시험의 가짜 주문 ID를 `o1`처럼 적었다가 출력 모델(소문자 UUID만 받음)이 거부했습니다. 모델이 맞게 막은 것이라 시험 값을 UUID로 고쳤습니다.
- **기준일 D(11-07):** 정답 대조 21건은 모두 그날 수집이 입력에 들어온 뒤에 만든 실행이라 옛 규칙과 새 규칙의 D가 같습니다. 그래서 21건 통과만으로는 새 규칙이 쓰이는지 알 수 없습니다 → 같은 실행을 다음 날 00:05Z로 옮긴 ⑫와, 엔진을 대역으로 바꿔 넘기는 D를 직접 보는 ⑩을 더했습니다(변이 "엔진에 실행 날짜 넘기기"는 21건으로는 안 잡히고 ⑩·⑫로만 잡힘).
- 계획의 ⑤("재고가 실행 날짜보다 미래")는 주문 한도가 함께 있으면 "실행 날짜 항 빼기" 변이를 잡지 못합니다. 주문 한도는 실행 날짜를 넘을 수 없어서(`confirm_t`까지 시작한 수집) min이 같아집니다. 시험을 짜다 알아채 ⑤를 "미래 재고일 + 주문 수집 없음"으로 짰고, 변이로 잡히는 것을 확인했습니다.
- **실제 데이터로 확인할 수 없는 갈래(11-08 다시 검증):** 내 DB의 주문 수집은 SUCCEEDED 365건·PARTIAL_SUCCESS 1건뿐이고(FAILED·RUNNING 없음), 2026-01-01 00:02Z에 첫 일 수집이 있어 초기 적재 처리가 결과를 바꾸는 실행이 없습니다. 실행 21건의 한도를 SQL로 따로 세어 `resolve_base_date`와 대조(원래 시각·다음 날 00:05Z 각 21건, 42건 불일치 0)했지만, "주문 상태 거르기 빼기"·"초기 적재 처리 빼기" 변이를 넣어도 이 대조는 불일치 0이었습니다 → 이 두 갈래는 단위 시험 ⑥·⑦로만 지켜집니다(두 변이 모두 단위 시험에서 잡힘).
- **운영 기준 검사(11-10):** 검사를 넣자 기존 시험 `test_build_passes_trigger_stage_and_expected_date_to_engine`이 깨졌습니다. 그 시험의 대역 엔진이 돌려주는 스냅샷(`{"snap": 1}`)에 운영 기준 키가 없어서입니다 → 그 시험은 검사 함수를 기록하는 대역으로 바꿔 "엔진이 만든 스냅샷으로 검사를 부르고, 엔진이 보류하면 부르지 않는다"만 보고, 검사 내용은 새 시험에서 봅니다.
