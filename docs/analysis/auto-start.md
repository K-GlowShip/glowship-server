# 분석 자동 시작 (GLOW-128, 이슈 #51)

지연 감지(AUTO)와 재분석(API 20)으로 만든 실행은 지금까지 `DETECTED`로 만들어지기만 했습니다. 이 문서는 그 실행을 서버 안에서 바로 분석하고 저장하는 실행기(`app/modules/delay_analysis/application/run_start/`)와, **왜 이렇게 만들었는지**를 적습니다.

> **지금은 꺼져 있습니다.** 실제 실행 묶음은 계약 도구 12개(T10 포함, #90)를 모두 등록해 만들 수 있고 재분석 → 분석 → 초안·최종 선택 끝까지 시험도 있지만(6절), 평가 시나리오 정답 대조와 3초·30초 측정이 아직 없습니다. 설정 `ANALYSIS_AUTO_START_ENABLED`의 기본값은 `false`이고, 꺼져 있으면 지금처럼 실행이 `DETECTED`로 남습니다. 켜는 조건과 방법은 7절에 있습니다(사용자 결정 11-09·11-10).

## 2. 실행기

| 항목 | 내용 | 이유 |
| --- | --- | --- |
| 어디서 도나 | 서버 프로세스 안 asyncio 작업(`AnalysisRunner`). 서버에 하나(`app_runner.get_analysis_runner`) | 실행을 만든 커밋 직후 같은 프로세스에서 바로 시작해 3초 시작(NFR-001)을 가장 단순하게 지킴. API 25 수동 수집의 백그라운드 적용과 같은 자리. 두 번째 프로세스·큐가 저장소에 없음(사용자 결정 11-08) |
| 동시 실행 수 | `ANALYSIS_MAX_CONCURRENT_RUNS`(기본 4). 차면 `DETECTED` 그대로 기다림 | 실행 하나가 워커 세션을 씀(풀 15개). 기다리는 실행이 `DETECTED`여야 서버가 죽어도 안전하게 다시 시작할 수 있음 |

| 시간 제한(이슈 #123) | 두 구간. **분석** = 시작 전이 ~ 그래프 끝(`ANALYSIS_RUN_TIME_LIMIT_SECONDS`, 기본 120초, 자리를 기다린 시간은 뺌): 넘으면 그래프를 취소하고 새 세션으로 지금 단계 `FAILED`(`RUN_TIME_LIMIT_EXCEEDED`, 시도 1, 소진 아님, "분석이 제한 시간 안에 끝나지 않아 중단했습니다. 잠시 뒤 재분석을 요청하세요."). 시작 전이에서 넘으면 `DETECTED` 그대로. **저장** = 결과 저장(저장 직후 재판정의 판정 서명 재계산 포함, `ANALYSIS_SAVE_TIME_LIMIT_SECONDS`, 기본 60초): 넘으면 되돌리고 재계산 없이 다시 저장(걸린 변경이 있으면 `STALE`), 그것도 30초를 넘으면 `FAILED`. 넘었는지는 예외 종류가 아니라 제한이 끝났는지로 보고, 서버 종료의 취소는 바꾸지 않음. 실행기 기본은 제한 없음이고 앱 조립만 설정값을 넘김 | 멈춘 실행이 자리를 계속 차지하고 그 지연의 재분석이 `RUN_IN_PROGRESS`로 막히는 것을 끝냄(agentflow 5.5·7.1 "정해진 시간 예산"). 저장을 따로 세는 이유: 재계산은 걸린 수집 하나에 12~14초라 분석을 다 하고 저장에서 버리지 않게. 값은 dev 사양(Docker CPU 1·2GB) 한 건 최악 약 47초(저장소 읽기 25초 + 실제 모델 설명 예산 20초)의 두 배 남짓, **측정 전 잠정값**. 30초(NFR-001)는 끊는 기준이 아니라 측정 목표(7절 3번) |
| 메모리(이슈 #123) | 그래프가 끝나면(예외·제한 포함) 실행 묶음의 엔진 입력을 놓음(`AnalysisRuntime.release`) | 노드 안 타이머가 취소돼도 예정 시각까지 그 실행 문맥을 붙잡아, 놓지 않으면 엔진 저장소(0.3~0.5GB)가 끝난 뒤에도 남음(`docs/analysis/engine-store-cache.md` 5절) |
| 세션 | 워커 역할(`open_worker_session`). 시작·단계 전이·저장은 짧은 세션마다 하나, 그래프(엔진 입력·노드 경계 상태 조회)는 실행 동안 읽기 세션 하나 | 요청 사용자가 없음(#48 리뷰). 분석 준비에서 DB 오류가 나면 그 세션은 실패한 트랜잭션이라 같은 세션으로 저장할 수 없음(#68 리뷰) → 저장은 새 세션 |
| 시각 | 가상 시각(`VIRTUAL_CLOCK_START`)이면 저장 끝난 시각·설명 생성 시각에 실행 시작 시각을 넘김. 아니면 넘기지 않음(DB 시각·서버 시각) | 이슈 #50 결정(부르는 쪽이 시각을 넘김). 저장 함수가 끝난 시각 = 시작 + 1초를 보장해 설명 생성 ≤ 끝남 |
| 실행 묶음 | `engine_runtime.build_engine_runtime(db, run, *, clock, tracer=None)`: 실제 조회 T1~T5·T8, 재고 영향 T6·T7, 대응안 T9·T10·T11, 최종 확인 T12, `decision_of`, 설명 생성(#45·#69) | 계약 도구 12개가 모두 등록돼 빠진 도구가 없음(T10은 `pure_tool(calculate_option_outcomes)`) |
| 추적 | 실행기 `tracer_factory(run) -> RunTracer | None`: 실행마다 시작 전이 뒤 하나를 만들어 실행 묶음(도구·설명 시도)과 그래프 콜백(실행·노드·갈림길)에 같이 넘기고, 끝나면 `aclose()`. 만들기·닫기 예외는 경고만 남기고 분석은 계속(만들기 실패면 추적 없이). 앱 실행기는 `AGENT_TRACE_DIR`가 있으면 내부 로그(`TraceOutboxSink`, `<폴더>/agent_trace_outbox/<고객사>/<UTC 날짜>.jsonl`)에 남기고, 싱크 하나를 모든 실행이 같이 씀. 비어 있으면(기본) 추적 안 함 | 실행 하나의 사건이 한 추적기로 이어져야 함(`docs/agent-flow/agent-tracing.md`). 동기 `close()`는 이벤트 루프를 멈춰 다른 실행의 도구가 시간 초과로 잡힘(#42 리뷰). 추적 장애가 분석을 막지 않음(agentflow 8.1). 줄이 섞이지 않게 하는 잠금이 싱크마다라서 하나를 같이 씀. 기본 비움은 배포 컨테이너(`USER app`, 코드 root 소유)에 쓸 수 있는 폴더가 아직 정해지지 않아서(사용자 결정 11-11) — agentflow 8.1 "외부 전송 불허 시 내부 서버 로그에 전량 저장"과 다르고, 폴더를 정해 넣으면 같아짐. 파일 날짜는 서버 시각(가상 시각으로 쓰면 며칠치 실행이 한 파일에 몰림) |
| 기준일 D | 실행 묶음이 엔진 입력의 `EngineInput.base_date`(#67)를 도구 문맥에 넣음 | 그날 재고·주문 자료가 입력에 없으면 D가 실행 날짜보다 당겨짐. 실행 날짜를 넣으면 T1 입력 확인이 실패함(#67 리뷰) |

## 3. 상태 전이와 저장

| 단계 | 하는 일 | 잠금 | 규칙 |
| --- | --- | --- | --- |
| 시작 전이 `begin_analysis` | `DETECTED → VALIDATING` | L2만 | `DETECTED`일 때만. **에피소드 열림·현재 실행 여부는 보지 않음**: 회복(`DELAY_RECOVERED`) 실행은 수집이 실행을 만든 뒤 같은 트랜잭션에서 에피소드를 닫으므로(#63) 닫힌 에피소드에서 시작해 `NO_DELAY`로 끝나야 함(확정 DB E8 v2). 현재 실행이 아니면 경고 로그만 남기고 시작(건너뛰면 영원히 `DETECTED`) |
| 단계 전이 `advance_status` | 그래프 상태의 `step`이 바뀔 때마다 `ANALYZING_IMPACT`·`ANALYZING_OPTIONS`·`VALIDATING_OUTPUT`으로 | L2만 | 진행 중이고 앞으로 가는 전이만. 그 사이 `STALE`이 됐으면 아무것도 바꾸지 않음(명세 8절 "진행 중일 때만 상태 전이") |
| 저장 `save_graph_outcome` | 종료 상태별 저장 함수(아래 표) | L2 | 저장 함수가 진행 중일 때만 씀 |
| 입력 데이터 버전 | 보류(`ON_HOLD`)가 아니면 저장과 같은 트랜잭션에서 `record_input_data_versions`. 그래프 밖에서 끝내는 `FAILED`(마지막 잡기·시작 정리, `fail_unfinished`)도 같음 | — | 입력 검증을 통과한 실행에만 기록하는 규칙(`run_creation_service` 머리말, 사용자 결정 11-10). 확정 DB는 보류 실행만 0건, 나머지는 도메인 5건. 재분석 실행은 만들 때 기록하지 않아 여기서 채워짐. 이미 있으면 다시 넣지 않음 |

**데이터 버전 기록 시점이 문서·경로마다 다릅니다(11-10 확인).**

| 근거 | 기록 시점 | 보류 실행 |
| --- | --- | --- |
| serviceflow 5.2 처리 단계 1·4 | 실행을 만들 때(재분석도 "1단계부터") | 5건 |
| 확정 DB(실행 21건) | — | 보류 1건(자동 실행 `EPISODE_STARTED` v1)만 0건, 나머지 20건 5건 |
| `run_creation_service` 머리말 | 입력 검증을 통과한 뒤 | 0건 |
| 지금 코드 | 자동 실행은 만들 때 무조건(`auto_run_service`, #63), 재분석 실행은 이 문서의 저장 때 | 자동 실행 5건, 재분석 실행 0건 |

이 PR은 확정 DB와 `run_creation_service` 규칙을 따릅니다. 자동 실행이 보류로 끝나도 5건이 남는 것은 실행 생성 쪽 코드라 이 PR에서 바꾸지 않았고, 생성 담당에게 "입력 검증 통과 뒤 기록"으로 옮기자고 요청합니다. serviceflow 5.2 문구는 설계 담당에게 고침을 요청합니다.

**맞춤(2026-11-11):** 자동 실행을 만들 때의 기록을 뺐습니다(`auto_run_service`). 이제 모든 경로가 "입력 검증을 통과한 실행만 결과 저장 때"이고, 자동 실행도 보류면 0건·나머지는 저장 때 5건입니다. 자동 시작이 꺼져 있는 동안(`DETECTED`) 실행 상세 `dataVersions`는 빈 목록입니다. serviceflow 5.2 처리 단계 1·입력 확정 행도 같은 뜻으로 고쳤습니다.

L1(고객사 잠금)은 잡지 않습니다. 실행 행 하나만 바꾸고, 수집 적용(L1 → L2)과 서로 기다리는 순환을 만들지 않기 위해서입니다.

| 그래프 종료 | 저장 함수 |
| --- | --- |
| `READY_FOR_REVIEW`·`NO_RISK` | `save_analysis_result`(저장 뒤 재판정) |
| 설명 3회 실패 | `save_analysis_failure`(계산 결과·모델·프롬프트 판) |
| 도구 실패·보류·도구 밖 예외 | `save_analysis_failure` |
| `NO_DELAY` | `save_no_delay`(이번에 만듦, `result-save.md` 9절) |
| `STALE`(노드 경계) | 저장 안 함(수집이 이미 바꿈) |

**동시 상황.** 모든 경쟁은 L2 하나로 차례가 정해지고, 시작·단계 전이·저장 모두 "진행 중일 때만"이라 `STALE`을 덮어쓰지 않습니다.

| 상황 | 결과 |
| --- | --- |
| 수집 STALE이 시작 전이보다 먼저 | 시작 전이가 `STALE`을 보고 시작하지 않음 |
| 시작 전이가 먼저, 분석 중 수집 STALE | 다음 노드 경계에서 그래프가 멈춤. 경계 전에 끝났으면 저장 함수가 `STALE`을 보고 쓰지 않음 |
| 같은 실행에 재분석 요청 | 진행 중(`DETECTED` 포함)이면 `RUN_IN_PROGRESS`로 거부 |
| 저장과 최종 선택 | 저장 전엔 `RUN_NOT_READY`, 저장 뒤 허용 |

## 4. 시작 위치

| 실행 | 시작 위치 | 이유 |

## 5. 서버 시작·종료와 전제

- **시작 정리(`sweep_on_startup`):** 서버가 시작될 때 끝나지 않은 실행을 찾아 `DETECTED`는 다시 시작하고, 분석 도중 멈춘 실행(`VALIDATING`~`VALIDATING_OUTPUT`)은 그때 단계로 `FAILED`(`UNEXPECTED_TOOL_ERROR`, 시도 1, "서버가 다시 시작돼 분석이 중단되었습니다. 재분석을 요청하세요.")로 끝냅니다. 그래프는 중간 결과를 남기지 않아 이어서 할 수 없고, 처음부터 자동으로 다시 돌리면 같은 실행이 서버를 계속 죽일 때 끝없이 반복됩니다(사용자 결정 11-08). 실행 하나를 `FAILED`로 바꾸다 예외가 나면 로그만 남기고 다음 실행으로 넘어가 서버는 뜹니다(그 실행은 진행 중으로 남아 다음 시작 때 다시 정리). 남은 실행 조회 자체가 실패하면 설정·권한 잘못이라 서버 시작을 멈춥니다.
- **닫힌 지연의 시작 전 실행(이슈 #51, 사용자 결정 11-11):** `DETECTED` 실행을 다시 시작하기 전에 `retire_unstarted_run_of_closed_episode`로 확인합니다. 지연이 닫혔고(입고 종료, 운영 기준 없는 날 회복 건너뜀) 회복 실행(`DELAY_RECOVERED`)이 아니면 시작하지 않고 `STALE`로 끝냅니다. 닫힌 지연은 초안·최종 선택·재분석이 모두 `EPISODE_CLOSED`로 거부되어 분석해도 쓸 수 없고, 켜는 순간 꺼진 동안 쌓인 이런 실행이 새 지연 분석보다 먼저 줄을 서기 때문입니다.
  - 사유는 정상 후속 판정과 같게: 회복으로 닫힘 `DELAY_SCHEDULE_CHANGED`, 입고로 닫힘 `DELAY_STAGE_CHANGED`(단계가 `RECEIVED`로 바뀜). 감지 순번·시각은 닫은 SHIPMENT 수집의 적용 순번·완료 시각입니다(`delay-detection.md` 5절과 같은 규칙). 닫은 수집 = 그 선적의 스냅샷 중 관측 시각이 `closed_at`과 같은 것을 남긴 수집입니다. 하나로 찾지 못하면 바꾸지도 시작하지도 않고 경고만 남깁니다(다음 시작 때 다시 봄).
  - 시작 전이 `begin_analysis`는 바꾸지 않았습니다. 확정 데이터는 지연 8건이 모두 닫혀 있어, 정답 대조(GLOW-58 2단계)가 닫힌 지연의 실행을 `DETECTED`로 되돌려 실행기로 돌리기 때문입니다. 수집 직후·재분석 직후에 넘기는 실행은 방금 만든 실행이라 그 시점에 지연이 열려 있거나 회복 실행이므로, 닫힌 지연의 비회복 실행을 시작하는 길은 시작 정리 하나뿐입니다.
  - 덮지 않는 것: 수집 직후 넘겨받아 동시 실행 자리를 기다리는 사이 지연이 닫히면 그 실행은 분석됩니다(결과는 닫힌 지연의 이력으로 남음). 자동 시작이 꺼져 있는 동안에는 지금처럼 `DETECTED`로 보입니다.
  - **설계 문서와 다른 점(설계 담당이 리뷰에서 동의, serviceflow 문구는 설계 쪽에서 보완):** serviceflow 4절 "닫힌 에피소드의 실행은 동결(STALE 판정 대상 아님)"과 달리 시작 전 실행에 한해 닫힌 뒤 `STALE`을 기록하고, 입고 종료 때 "이전 실행 그대로"와 달리 시작 전 실행만 `STALE`로 바꿉니다. 수집 변경에 따른 STALE 판정은 여전히 하지 않습니다. 또 serviceflow 4절 "실행 생성이 실패하면 지연 에피소드는 열린 채 남는다"는 회복 판정이 건너뛰어진 경우를 빠뜨렸습니다(이때는 닫힘).
- **모든 고객사 보기:** 앱·워커 역할은 고객사 문맥 없이 `analysis_runs`·`companies`를 한 행도 보지 못합니다(고객사 행 보안). 그래서 DB 함수 `app_worker_find_unfinished_runs()`(리비전 0009, `SECURITY DEFINER`, 워커 역할만 실행)가 끝나지 않은 실행의 (고객사, 실행 ID, 상태)만 돌려주고, 바꾸는 일은 고객사 문맥을 넣은 평소 세션이 합니다. 0001 관리자 사용자 생성·0008 로그인 조회와 같은 방식입니다(사용자 결정 11-09). 로컬 superuser는 정책을 건너뛰어 함수 없이도 보이므로, 이 문제는 운영 역할에서만 드러납니다.
- **마지막 잡기:** 그래프 밖으로 나온 예외(연결 실수 `RuntimeWiringError`, LangGraph 오류, 저장 예외)는 새 세션으로 지금 단계 `FAILED`를 한 번 더 저장하고, 그것도 실패하면 `critical` 로그만 남깁니다. 그 실행은 다음 시작 정리가 끝냅니다.
- **종료:** 돌던 작업을 `ANALYSIS_SHUTDOWN_GRACE_SECONDS`(기본 10초) 기다리고 남은 것은 취소합니다. 취소는 잡지 않으므로(#68) 진행 중으로 남고 다음 시작 정리가 `FAILED`로 끝냅니다.
- **전제: 서버 프로세스 하나.** 둘 이상이면 한 프로세스의 시작 정리가 다른 프로세스가 정상으로 돌리는 실행을 `FAILED`로 만들 수 있습니다. 그때는 실행에 임대(맡은 프로세스·심박) 열을 더하거나 정리를 한 프로세스만 하게 바꿔야 합니다. 지금 배포(`make dev`, `uvicorn` 하나)는 하나입니다.

## 8. 작업 중 실패와 원인

- **끝까지 시험의 업무 값 확인이 늘 참이었음(11-11, push 전 리뷰):** 처음에는 추적 파일에 주문 코드(`-ORD-`)가 없는지만 봤습니다. 그런데 추적기는 단계·결과 코드만 값으로 남기고 이 실행은 위험 주문이 없어, 주문 코드가 들어갈 길이 없었습니다(마스킹이 꺼져도 통과). DB에서 그 지연의 선적·고객사·SKU 코드를 읽어 파일에 없는지 보도록 바꿨습니다. 추적기는 두 겹(안전 키만 값으로, 객체는 이름만)으로 막아, 한 겹만 풀어서는 업무 값이 새지 않아 시험도 통과합니다("안전 키 필터 없앰" 변이는 못 잡음). 두 겹을 모두 풀어 객체까지 펼쳐 남기면 잡히는 것을 확인했습니다.
- **시험이 개발자 설정에 좌우됨(11-11, push 전 리뷰):** 앱 실행기 시험이 실제 설정을 복사해 쓰는데, `.env`에 `AGENT_TRACE_DIR`를 넣으면 기존 켜기 확인 시험이 그 폴더를 만들거나(쓸 수 있을 때) 실패했습니다(못 쓸 때). 시험 도우미가 추적 폴더를 기본 없음으로 둡니다.
- **끝까지 시험의 기대값 하나를 재지 않고 적음(11-11, 재분석 끝까지 시험):** 설계 때 "분석 뒤 데이터 버전 5건"을 코드(저장 단계에서 기록)만 보고, 구현 전에 롤백으로 돌려 본 확인의 값처럼 적었습니다. 그 확인은 이 값을 세지 않았습니다. 구현 전에 다시 돌려 재분석 직후 0건 → 분석 뒤 5건을 실제로 확인했습니다.
- **확정 데이터로는 재분석 끝까지 시험을 만들 수 없음(11-11):** 확정 데이터 지연 8건이 모두 닫혀 재분석·초안이 `EPISODE_CLOSED`입니다. 지연을 다시 열어도 최신 순번에서는 그 선적이 이미 입고돼 `NO_RISK`가 나옵니다(입고로 닫힌 지연 3건을 다시 열어 재분석해 확인, 롤백). 데모 시드로 최신 순번에서 열린 지연을 만듭니다(시드 결과가 독립 기대값이 되는 장점도 있음, 6절).
- **시작 정리 시험의 준비가 되돌려짐(11-11, 닫힌 지연 처리):** 시작 정리는 끝나지 않은 실행을 조회한 뒤 그 세션을 `rollback`합니다. 시험이 같은 세션을 실행기에 넘기면(저장점 모드) 시험에서 `DETECTED`로 되돌린 값까지 함께 취소되어, 처음 쓴 실제 DB 시험이 모두 "이미 STALE이라 시작 안 함"으로 실패했습니다. 시험 준비를 마친 뒤 저장점을 커밋하고(끝나면 바깥 트랜잭션을 롤백) 실행기를 부릅니다(`test_run_start_sql.py` `_detected`). 또 시작 정리는 DB의 `DETECTED`를 모두 가져오므로 결과 목록은 "포함 여부"로 비교합니다(개발 DB에 다른 `DETECTED`가 있어도 통과).
- **실제 실행 묶음을 만들 수 있다고 봄:** 계획 때 T10이 develop에 있는지 확인하지 않았습니다. 등록표에 도구가 하나라도 없으면 `AnalysisRuntime`이 만들 때 멈춥니다(`runtime.py` 105~108행). 그래서 설정으로 꺼 둔 채 넣기로 했습니다. push 직전 재검증 때 T10이 #90으로 들어와 있었지만, 끝까지 시험 없이 등록하지 않기로 했습니다(사용자 결정 11-10).
- **고객사 구분 없는 조회를 놓침:** 시작 정리를 처음 설계할 때 행 보안을 보지 않았습니다. 로컬 superuser에서는 보여서 시험으로도 드러나지 않습니다. 함수(0009)로 풀고, 워커 역할로 바꿔 직접 조회가 0행인 것을 시험으로 고정했습니다.
- **데이터 버전을 시작 전이에서 기록함:** 처음에는 시작 전이에서 기록했는데, 입력 검증을 통과한 실행에만 기록하는 규칙과 확정 DB(보류 0건)에 어긋났습니다. 저장 단계로 옮기고 보류는 빼, 시험 두 건으로 0건·5건을 확인합니다.
- **커밋 뒤 ORM 객체를 읽음:** 시험 세션은 커밋 때 객체를 만료시켜, 커밋 뒤 실행 값을 읽다 `MissingGreenlet`이 났습니다(운영 워커 세션은 만료를 끔). 시작한 실행은 값을 복사한 `StartedRun`으로 넘기고, 재분석 서비스는 돌려줄 값을 커밋 전에 만듭니다.
