# 엔진 입력 저장소 (한 고객사·한 입력 순번, 서버 DB에서 읽기)

- 대상: `app/modules/delay_analysis/infrastructure/engine/engine_input_store.py`, 시험 `tests/modules/delay_analysis/test_engine_input_store.py`
- 티켓: GLOW-125 (FR-008 관련 자료 조회. 인수 조건 "해당 고객사의 자료만 조회되고, 사용한 데이터와 기준 버전이 실행에 기록된다")
- 쓰는 곳(다음 작업): 조회 도구 T1~T5·T8, 재고 영향·위험 주문 T6·T7(엔진 `snapshot.build` → `pipeline.analyze`)
- 고친 이력: PR #36 1차 리뷰(11-05)로 2·4·5절이 바뀜. 입력 순번으로 거르기, 1초 미만 시각, 스레드 처리, 엔진 소스 해시

## 1. 왜 필요한가
- 엔진의 입력 스냅샷 `snapshot.build(store, …)`는 업무 DB를 메모리에 올린 `Store`를 받습니다.
- 엔진 `Store`는 `docker exec <컨테이너> psql -U postgres`로 **DB 전체(모든 고객사)**를 읽습니다(`store.psql_copy`). 서버에서는 쓸 수 없습니다.
  - 컨테이너·계정이 정해져 있습니다.
  - 고객사 범위가 없습니다(BR-001).
- 엔진 원본은 고치지 않기로 했습니다(`engine-local-path.md`). 그래서 **읽는 부분만** 서버 연결로 바꾸고, as-of 조회와 스냅샷은 엔진 것을 그대로 씁니다.

## 2. 방식
| 단계 | 내용 |
| --- | --- |
| 고객사 범위 | RLS 컨텍스트 `app.company_id`를 설정하고, 조회 조건에도 `company_id = $1`을 넣습니다. RLS가 우회되는 로컬 superuser 접속에서도 다른 고객사 행은 읽히지 않습니다(`run_status_repository`와 같은 방식) |
| 읽는 표 | 엔진 `store.TABLES` 14개 + 변경 기록(엔진 `DCR_SQL` 범위). 서버 쪽 허용 목록 `ENGINE_TABLES`와 엔진 목록이 다르면 멈춥니다(엔진 새 판 감지, SQL에 넣는 표 이름 제한) |
| **입력 순번으로 거름** | 저장소 하나 = **(고객사, 실행의 `input_seq`)** 하나입니다(아래 표) |
| 읽는 방법 | 엔진과 같은 `COPY (…) TO STDOUT CSV HEADER`를 서버 연결(asyncpg `copy_from_query`)로 실행합니다. 엔진 변환 함수 `iso_ts`·`bool_text`를 그대로 씁니다 |
| 1초 미만 시각 | 서버 수집은 `datetime.now(UTC)`로 시각을 적어 마이크로초가 있고, 엔진 `iso_ts`는 1초 미만을 거부합니다. 그래서 **읽을 때 초 아래를 버립니다**(`floor_seconds`, 실행 시작 시각 `engine_timestamp`와 같은 규칙). 이슈 #39부터 서버 수집은 초 단위로 기록하지만, 그 전에 적재된 행이 있어 그대로 둡니다. 그 밖의 해석 오류는 `EngineInputError`(열·값 포함)로 알립니다 |
| 행 순서 | `ORDER BY ctid`. 엔진은 조건 없이 전체를 읽어 물리 순서로 받습니다. 조건을 걸면 색인 순서로 올 수 있어 순서를 맞춥니다(5절) |
| Store 만들기 | 엔진 `Store`를 상속합니다. `__init__`(색인 만들기)은 엔진과 같은 식으로 옮겨 적었습니다. `input_seq`는 적재된(순번 있는) 수집만 보도록 덮어썼습니다(엔진 원본은 `RUNNING`·`FAILED`의 빈 순번에서 `int('')`로 멈춤). 나머지 as-of 메서드는 엔진 것을 그대로 씁니다. 색인을 다 만든 뒤 `defaultdict` 6개를 없는 열쇠를 넣지 않는 사전으로 바꿉니다(캐시로 여러 실행이 함께 읽어서, `engine-store-cache.md` 4절) |
| 이벤트 루프 | CSV 해석과 색인 만들기는 무거우므로(한 고객사 수 초) `asyncio.to_thread`에서 합니다. 같은 서버의 다른 요청이 기다리지 않게 하려는 것입니다(GIL 때문에 완전한 분리는 아님, 4절) |
| 빈 읽기 확인 | RLS로 보이지 않으면 오류 없이 0행이 됩니다(앱 역할 세션, ACTIVE가 아닌 고객사, 없는 고객사). `companies`가 정확히 1행이고 `data_sync_runs`가 비어 있지 않은지 확인해, 아니면 `EngineInputError`로 멈춥니다(빈 Store로 계산하지 않게, 리뷰 KatherineJH) |
| 마지막 확인 | `check_input_seq`: 엔진의 시각 기준 순번이 실행의 `input_seq`와 같은지 봅니다. 순번으로 거른 뒤라 정상이면 같고, 다르면 `EngineInputError`입니다 |

### 입력 순번으로 거르는 표 (PR #36 리뷰 [critical] 반영)
> 이슈 #39(`fix/GLOW-13-sync-timestamps-engine-rules`)부터 서버 수집은 시작 시각을 **적용 때 L1 안에서 확정**합니다(고객사 마지막 적재 수집 시작 + 1초보다 늦게, `docs/data-sync/ingest.md` 1절 수집 시각 규칙 5). 그래서 새로 적재되는 수집은 시작 시각 순서 = 적용 순번 순서입니다. 아래 거르기는 그 전에 적재된 수집과 방어용으로 남깁니다.

이슈 #39 전의 서버 수집은 시작 시각을 **L1 잠금 전에** 정했습니다(`ingest_service.py` `started_at = self.now()` → `lock_company`). 그래서 겹친 수집에서는 "시작 시각 순서"와 "적용 순번 순서"가 다릅니다. 예를 들면 이렇습니다.
1. ORDER 수집이 먼저 시작해 L1을 기다립니다.
2. 그동안 SHIPMENT 수집이 실행을 만듭니다(`input_seq = N`).
3. ORDER가 `N+1`로 커밋됩니다.

엔진은 시각 기준이라 이 ORDER를 입력에 넣습니다. 실행 생성(#21)과 B의 STALE 판정은 순번 기준이므로, 읽을 때 순번으로 맞춥니다.

| 표 | 처리 | 이유 |
| --- | --- | --- |
| `data_sync_runs` | 적용 순번 ≤ `input_seq`인 것 + 순번이 없는 `RUNNING`·`FAILED` | 순번이 없는 수집은 엔진처럼 시각으로 판단하게 둡니다("그날 주문 수집이 시작됐는가" 규칙) |
| `inventory_daily`, `shipment_schedule_snapshots`, `data_validation_issues` | 행을 만든 수집의 적용 순번 ≤ `input_seq`인 것만 | 수집이 만든 행이라 그 수집이 입력 밖이면 빼야 합니다 |
| 주문·주문 상세·선적·선적 상세·상품·창고·운영 기준·매핑·고객사 | 거르지 않음 | 현재 상태 표입니다. 주문·선적의 `data_sync_run_id`는 "마지막으로 고친 수집"이라 거르면 이전부터 있던 행이 빠집니다. 그 시점의 상태는 엔진의 시각 규칙(접수일 + 1 수집, 변경 기록)으로 되돌립니다 |
| 변경 기록(`DCR_SQL`) | **거르지 않음** | 엔진은 나중 수집의 변경 기록(출고 기록 등)으로 현재 상태를 그 시점의 상태로 되돌립니다(`dispatch_date` → `order_open_at_close`). 거르면 출고된 주문이 처음부터 출고된 것으로 보여 예약 복원이 DB와 달라집니다(5절) |

- **겹친 수집의 결과:** 늦게 커밋된 ORDER는 이 실행의 입력에 들어가지 않습니다. 그날 주문 수집이 없는 것으로 보아 엔진 R-05 규칙대로 **보류**(`REQUIRED_DATA_INVALID`, "ORDER 수집 결측일 …")가 됩니다(#36 리뷰에서 롤백 재현으로 확인한 코드. 처음 적은 `MISSING_REQUIRED_DATA`는 틀렸음). 이미 `ON_HOLD`로 끝난 실행은 STALE 대상이 아니므로(`analysis_runs_ck25`, `STALE_TARGET_STATUSES`) 늦게 커밋된 ORDER가 이 실행을 다시 분석하게 하지는 않습니다. 사용자 재분석(D18)이 있어야 다시 분석합니다. 안전하게 멈추는 동작이라 코드는 그대로 두고, 수집 쪽 시각 규칙(이슈 #39)에서 겹침 자체를 줄입니다.

```python
store = await load_company_engine_store(
    session, company_id, run.input_seq
)  # 워커 세션, 읽기 전용
confirm_t = engine_timestamp(run.started_at)
check_input_seq(store, company_id, confirm_t, run.input_seq)
snap = load_engine_module("snapshot").build(
    store, calendar, shipment_id, D, confirm_t, stage=..., E=...
)
```

## 4. 측정과 확인이 필요한 것
- **읽는 시간:** A_BEAUTY 한 고객사·한 순번에 약 9.5초가 걸립니다.
  - 주문 10.7만·주문 상세 16만·재고 3.6만 행, 변경 기록 26.6만 행입니다.
  - 대부분 Python의 CSV 해석과 시각 변환입니다.
  - 감지 후 30초 안 결과(NFR-001)를 생각하면 커서 실행기 연결(GLOW-128·129) 때 정합니다.
  - 후보: ① (고객사, 입력 순번, `max(applied_seq)`)가 같으면 워커 안에서 다시 쓰기(LRU로 고객사 수만큼 메모리 상한). 입력 순번이 같아도 그 사이 STALE 판정용 변경 기록이 늘 수 있어 마지막 적용 순번을 열쇠에 함께 넣습니다(리뷰 KatherineJH) ② 분석 워커를 API와 다른 프로세스로 두기(`to_thread`로도 GIL을 다 피하지 못함, 리뷰 [should]).
  - **정함(11-09):** 자동 시작은 API 서버 안 asyncio 작업(이슈 #51), 캐시 열쇠는 **(고객사, 입력 순번)**(이슈 #60, `engine-store-cache.md` 2절). 서버 STALE 판정은 이 저장소를 읽지 않고 SQL로 판정해, 변경 기록이 늘어도 캐시와 상관없어 ①의 마지막 적용 순번은 넣지 않았습니다.
- **실행 시작 시각:** `create_analysis_run`은 `clock_timestamp()`(마이크로초 포함)를 씁니다. 엔진 입력에는 초 아래를 버린 시각을 넘깁니다. 같은 초 안의 앞뒤가 사라질 수 있지만, 순번으로 거르기 때문에 입력 범위는 바뀌지 않습니다.
- **같은 초에 시작한 수집(수집 쪽 조건):** 엔진은 고객사 안에서 수집을 **시작 시각 하나로 구분**합니다(`store.run_at` 열쇠 `(company_id, started_at)`, `stale.judge`가 변경 기록을 시작 시각으로 묶음). 이 저장소는 초 아래를 버리므로, 같은 초에 시작한 두 수집은 같은 시각이 되어 한쪽이 가려집니다. 수집 적재가 "초 단위, 고객사 안에서 시작 시각이 겹치지 않음"을 지키도록 수집 담당(B, GLOW-13)이 맞추기로 했습니다(PR #36 리뷰 KatherineJH). overlay는 원천마다 1분씩 띄워 겹치지 않습니다. 이슈 #39에서 맞췄습니다(`docs/data-sync/ingest.md` 1절 수집 시각 규칙 1·4).
- **엔진 상수:** 엔진 `DCR_SQL`은 `started_at >= '2026-01-01'`로 고정돼 있습니다. 엔진 판의 결정이라 서버는 그대로 따릅니다.
- **도구(2부)에 넘길 메모:** 도구 모델의 시각은 초 단위(`…:SSZ`, #26)입니다. 도구 출력에도 같은 규칙(초 아래 버림)을 씁니다. 실행의 공식 데이터 버전은 엔진 스냅샷의 `data_versions`(시각 기준)가 아니라 실행 생성 때 기록한 `analysis_run_data_versions`(#21, 순번 기준)입니다.

## 5. 작업 중 실패와 결정
- **행 순서(11-05):** 처음에는 고객사 조건만 걸어 읽었습니다. 정답 대조에서 B_COSMETICS의 `skus` 순서가 엔진과 달랐습니다(내용은 같음). 고객사 조건 때문에 DB가 색인 순서로 돌려준 것입니다. `ORDER BY ctid`로 물리 순서를 맞췄습니다.
- **탐색 스크립트의 가짜 오류(11-05):** 스냅샷 비교를 JSON으로 하다가, 스냅샷의 튜플 키 때문에 `TypeError`가 났습니다. 이것을 `snapshot.build` 실패로 잘못 읽을 뻔했습니다. 시험은 `==`로 비교합니다.
- **엔진 경로(11-05):** 처음에 `synth2025_v5`와 Q9 수정판이 없는 묶음 경로로 돌려 실제 엔진 시험이 실패했습니다. 준비된 묶음(`engine-local-path.md` 2절)으로 돌려야 합니다.
- **결정을 바꿈: 읽을 때 순번으로 거름(PR #36 리뷰, 11-05):**
  - 처음에는 "엔진 판단(시각 기준)을 그대로 두고 같은지 확인만 한다"를 골랐습니다.
  - 리뷰에서 세 가지가 나왔습니다(코드로 확인함): ① 서버 수집은 마이크로초가 있어 엔진이 거부 ② 순번 없는 `RUNNING`·`FAILED`에서 엔진 `input_seq`가 멈춤 ③ 시작 시각을 L1 전에 정해 겹친 수집에서 시각과 순번이 갈림.
  - overlay는 모두 초 단위·완료 수집이라 시험에 드러나지 않았습니다. 특히 저는 마이크로초를 "함께 정할 일"로만 적어, 실제 AUTO 실행이 모두 서버 수집에서 시작한다는 점을 놓쳤습니다.
  - 서버의 다른 곳(실행 생성 #21, 상세 API #32, B의 STALE 판정)이 순번 기준이라 그쪽에 맞췄습니다. 수집 쪽을 고치는 안(L1 뒤 초 단위로 시각 기록)은 B 모듈이고, 진행 중인 #40과 같은 곳이라 고르지 않았습니다.
- **변경 기록까지 걸렀다가 되돌림(11-05):** 처음에는 변경 기록도 순번으로 걸렀습니다. 그러자 B_COSMETICS NO_RISK 실행(AN-260117-001)이 `REQUIRED_DATA_INVALID`(WH-EAST 01-16 예약 불일치)로 바뀌었습니다. 엔진은 나중 수집의 출고 기록으로 주문의 현재 상태를 그 시점으로 되돌리는데, 그 기록이 빠져 출고된 주문이 처음부터 출고된 것으로 보였기 때문입니다. 변경 기록은 거르지 않도록 되돌렸고, 정답 대조(실행별 21건)로 확인했습니다.
