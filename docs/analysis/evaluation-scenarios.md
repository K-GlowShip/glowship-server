# 평가 시나리오 10건 정답 대조 — 1단계·2단계·화면 통합 (GLOW-58)

GLOW-50 에서 만든 평가 시나리오 10건(공유 자료 `평가시나리오/`, 11-12 까지 이름은 `평가시나리오_검토용/`)을 서버 쪽에서 돌려 **수작업 정답표**와 맞춰 본 기록입니다.
기대값은 `02_시나리오와정답.md`(3절 요약표·5절 시나리오별 표)에서 옮겼고, 엔진 fixture 의 `EXPECTED` 는 쓰지 않았습니다.
**기준 정답은 GLOW-50 최종정답표 v6**(`GLOW-50_최종정답표_v6.md`, SHA-256 `7bbc15fd…`)입니다. 02 는 v6 를 바탕으로 정리한 검토용 문서라 파일이 달라질 수 있어, 옮긴 값이 v6 와 같은지는 기계로 대조합니다(8.9절).
시험은 모두 `tests/modules/delay_analysis/evaluation/` 에 있고 운영 코드는 바꾸지 않았습니다.
1~7절은 1단계(도구·설명을 하나씩), 8절은 2단계(실제 실행 경로 전체), 9절은 화면까지 통합한 상태에서의 확인(수작업, 11-13~11-15)입니다.

  - AI 설명 생성(GLOW-127 `generate_explanation`, mock 모델)과 T12 재검증, GS-06 보류의 서버 저장 모양(`hold_summary`)을 본다.
- **2단계(11-11, 8절):** 실제 도구 12개 묶음 → 실행기 → 저장까지의 실제 경로를 확정 DB 의 정답 실행 21건으로 돌려 저장 행을 정답과 견주고, 평가 시나리오 9건을 그래프 전체로 돌린다. 평가 시나리오를 DB 에 넣지는 않는다(8.1절). 화면까지 통합한 확인(9절)은 화면 확인용 DB 를 따로 만들어 시나리오 9건의 결과를 넣었다.

## 4. 발견 (엔진·다른 담당 몫, 결정 대기)

### 4.1 설명 검증기가 구분자 없는 SKU 코드 안의 숫자를 수치로 센다 — 평가 fixture 설명이 실패 (11-07 범위 바로잡음, 11-11 해결)

- **현상:** 엔진을 직접 불러도(서버 감싸기 없이) GS-02·03·07·08·09A·09B·10·11 의 mock 설명이 3번 모두 `VALUE_MISMATCH@risk_summary#s2` 로 실패합니다. GS-05(SKU `X`·`Y`)만 통과합니다.
- **원인:** `explain/textcheck.tokens` 가 "SKU별 지연 증분은 CREAM20 100개입니다" 에서 숫자를 `[20, 100]` 으로 셉니다. 문장이 인용한 값은 `[100]` 하나라 다중집합이 달라집니다(`validator.py` 의 1:1 대응 규칙). `CREAM20` 은 코드 토큰으로도 잡히지 않습니다. 코드 토큰 규칙(`textcheck.py` 12행 `CODE`)은 `-`·`_` 로 이어진 대문자 코드만 코드로 빼내므로, `SKU-005 31개` 는 `[31]` 로 맞게 셉니다. 숫자를 잘못 세는 것은 `CREAM20`·`SKU005` 처럼 구분자 없이 영문 뒤에 숫자가 붙은 코드뿐입니다.
- **영향:** 엔진 평가 fixture(GLOW-50)의 SKU 코드(`CREAM20`·`TONER50` …)로 만든 설명이 엔진 자기 검증기에 걸려, 평가 시나리오에서 설명 통과를 확인할 수 없습니다. 실제 DB 의 SKU 코드(`SKU-001` 모양, 구분자 있음)는 해당하지 않습니다 — overlay 실행 13건이 `SKU-005`·`SKU-026` 같은 코드로 설명 PASSED 로 저장돼 있습니다. 운영 SKU 코드가 구분자 없는 모양이면 같은 실패가 납니다.

## 5. 시험 방법과 음성 시험

- **정답표에서 옮김:** 기대값은 정답표 숫자를 그대로 적었고, 엔진 `EXPECTED` 는 참고하지 않았습니다. 정답표에 없는 값(탐침의 순위 등)은 엔진 대조만 합니다.

- **실제 경로의 조립:** 앱 실행기(`app_runner.build_app_runner`)를 가상 시각으로 만든 것 그대로입니다. 설명 생성 시각 = 실행 시작 시각, 저장 끝난 시각 = 시작 + 1초. 다른 것은 세션뿐입니다: 앱은 워커 접속을 새로 열고, 시험은 롤백 세션 하나를 실행기에 돌려주고 `SET LOCAL ROLE glowship_v4_worker` 로 워커 역할을 겁니다. 저장하는 순간의 DB 역할이 워커인지도 봅니다. 실행기가 세션을 열 때마다 RLS 문맥(`app.user_id`·`app.company_id`)을 비워 새 접속을 흉내 냅니다(실행기가 저장 세션에 문맥을 넣지 않으면 워커 역할에서 행이 보이지 않아 시험이 실패).
- **장치:** 조립은 따라 적지 않고 `build_app_runner` 를 가상 시각 설정으로 부릅니다(세션만 `open_session` 으로 바꿔 끼움, #121 이 넣은 인자). 그 위에 시험용으로 묶음 만들기(장애 주입)와 저장(상태·역할 기록)을 감싸고, 추적기는 시험이 넘긴 것을 씁니다. 설명 모델 설정(`EXPLANATION_MODEL`)이 mock 이 아니면 실제 경로 시험과 그래프 시험은 건너뜁니다(정답은 엔진 템플릿 설명으로 만들어졌고, 시험이 실제 모델을 부르지 않게).
- **장치의 세션과 시간 제한:** 장치는 롤백 세션 하나를 실행기에 돌려주되, 세션을 열 때 RLS 문맥을 비우고 세션이 끝날 때 커밋 안 한 것을 버립니다(앱은 세션마다 새 접속이고, 닫으며 버림). 실행기의 시간 제한(분석·저장)은 꺼 둡니다. 제한에 걸려 DB 질의가 도중에 취소되면 접속이 무효가 되는데, 앱은 그 접속을 버리고 새로 열지만 장치는 시험 트랜잭션 전체가 그 접속 하나라 이어 갈 수 없기 때문입니다. 정답 대조는 PC 속도와 상관없어야 하고, 제한에 걸린 뒤의 동작(다시 저장·`FAILED`)은 실행기 시험이 봅니다.
- **확정 DB 의 실행은 모두 끝난 상태**라, 실행 하나를 같은 트랜잭션 안에서 `DETECTED` 로 되돌려 다시 돌립니다. 되돌리는 순서는 실패 요약 비우기 → 결과 행·초안·최종 선택 지우기 → `DETECTED` 입니다(이 순서가 아니면 `ck10` 에 걸림). 시험이 끝나면 롤백합니다.

### 8.4 GS-09·GS-10 의 서버 쪽을 어떻게 다뤘나

- **GS-09(STALE 재판정·서명 재계산):** 시나리오 숫자 그대로는 서버에 넣지 않았습니다(시나리오가 DB 에 없음). 같은 규칙("서명이 같으면 유지")을 확정 데이터의 STALE 열로 견줍니다(8.5절). 처음에는 서버에 판정 서명 재계산기가 없어 정답과 다른 8건을 strict xfail 로 두었고, #116 으로 재계산기가 연결된 뒤 다시 대조했습니다. 정답표의 "R1 에 대한 최종 선택 시도는 거부"는 세 곳에서 봅니다(11-12 리뷰 후속). 판단 쪽 단위·API 시험(`test_selection_policy`·`test_final_decision_service`·`test_final_decision_api`)은 그대로 있습니다.
  - 1단계 `test_r1_final_selection_matches_answer_sheet`: 엔진이 낸 R1 상태(변경 A = `STALE`, 변경 B = `READY_FOR_REVIEW`)를 서버 최종 선택 판정(`selection_rejection`)에 넣습니다. A 는 409 `ANALYSIS_STALE`, B 는 거부 없음입니다. 두 경우는 상태만 다르고 나머지 입력은 같은 "선택할 수 있는 값"이라, 거부가 갈리는 이유는 STALE 하나입니다.
  - 2단계 G 연결 확인(8.5절): 실제 경로로 저장한 뒤 서명이 바뀐 수집에서 STALE 이 된 실행(일반 데이터 변경 → 서명 바뀜 → STALE, GS-09 변경 A 와 같은 모양)에 그 실행의 FEASIBLE 대응안으로 최종 선택을 요청하면 409 `ANALYSIS_STALE` 이고 최종 선택 행이 생기지 않습니다.
  - 2단계 B5(아래 GS-10): 후속 실행이 생긴 이전 실행.
- **최종 선택을 어느 계층으로 부르나:** 최종 선택 서비스(`FinalDecisionService.decide`, API 19)를 실제 저장소로 부릅니다. 분석은 워커 역할로 돌지만 최종 선택은 사용자의 요청이라, 워커 역할을 푼 뒤 앱 역할(`glowship_v4_app`)과 요청자(그 고객사 팀장)·고객사 RLS 문맥으로 부르고, 부르는 순간의 DB 역할도 단정합니다. 라우터가 하는 일(팀장 역할 확인, 오류 코드 → HTTP 응답 변환)은 판단 모듈 API 시험이 보므로 여기서 다시 세우지 않았습니다. 오류 코드가 HTTP 상태(409)를 함께 들고 있어 서비스가 낸 코드와 상태를 같이 단정합니다. 시간이 지나 대응안이 맞지 않을 때의 거부(`ANALYSIS_STALE_TIME_ELAPSED`)도 코드 문자열·상태가 같아(`ANALYSIS_STALE`, 409) 그것만으로는 STALE 때문인지 못 가르므로, 오류 멤버(`DecisionErrorCode.ANALYSIS_STALE`)까지 단정합니다. 요청자는 그 고객사의 활성 팀장입니다.
- **GS-10(지연 감지 → 후속 실행 생성):** 생성과 이전 실행 STALE 은 `test_auto_run_sql.py`, 수집 → 자동 시작 넘김은 `test_manual_sync_start_runs.py` 가 이미 봅니다. 여기서는 그 조각들을 실제 STALE 판정·실제 묶음으로 한 번 이어 붙였습니다(B5):
  1. 새 지연 선적 수집 → v1 `AUTO/EPISODE_STARTED`·`DETECTED`(입력 순번 = 그 수집) → 실제 경로로 끝 상태 저장(저장 뒤 데이터 버전 5건)
  2. 같은 선적의 예상 입고일을 10일 늦춰 다시 수집 → v1 `STALE`·`DELAY_SCHEDULE_CHANGED`(감지 순번 = 그 수집, 현재 버전 아님, 결과는 보존)
  3. v2 `AUTO/SCHEDULE_WORSENED`·부모 = v1·버전 2·입력 순번 = 그 수집·`DETECTED`
  4. v2 실제 경로로 끝 상태 저장(저장 뒤 데이터 버전 5건), v1 은 그대로 STALE
  5. 이전 실행(v1)에 최종 선택 요청 → 409 `ANALYSIS_STALE`, 최종 선택 행 0건, v1 은 STALE 그대로. v1 은 현재 버전도 아니지만(`NOT_CURRENT_RUN`) 판정 순서(`selection_rejection`)가 STALE 을 먼저 보므로 이 거부는 STALE 때문입니다. 현재 버전(v2)은 STALE 로 막히지 않고, 위험이 없어 선택 대기가 아니므로 `RUN_NOT_READY` 입니다(같은 요청이 실행 상태에 따라 다른 코드로 갈림)
- 새 선적은 지연 증분이 없어 두 실행 모두 `NO_RISK` 로 끝납니다. 시험은 두 실행의 끝 상태를 `NO_RISK` 로 단정하고 흐름·상태·연결을 봅니다. 대응안 숫자는 보지 않습니다. v1 은 대응안이 없어 5번은 없는 대응안 ID 로 요청합니다(STALE 확인이 대응안 확인보다 먼저). 대응안이 있는 STALE 실행의 거부는 G 연결 확인이 봅니다. GS-10 의 숫자(소진일 03-11 등)는 C 갈래와 1단계가 봅니다.
- 데이터 버전은 저장 뒤 건수만 봅니다(도메인 5개). 자동 실행은 만들 때가 아니라 결과를 저장할 때 기록합니다(#120). 만든 직후 0건인 것은 `test_auto_run_sql.py` 가 봅니다.
- 수집이 돌려준 실행 ID 를 실행기에 직접 넘깁니다. 수동 수집의 넘김(`start_runs`)은 거치지 않습니다.

### 8.8 작업 중 실패와 원인 (2단계)

- **주입 없는 대조에서 의존 범위까지 견주려 함:** RT-2 를 주입 없이 돌린 결과(READY)를 정답(설명 실패)과 의존 범위까지 견줬더니 달랐습니다. 설명 실패 저장은 의존 범위를 남기지 않습니다(정상 완료 값은 쓰지 않음, `result-save.md`). 판정 서명과 결과 행만 견주게 고쳤습니다.
- **시작 정리 시험이 세션을 동시에 씀:** 정리가 다시 시작시킨 실행(백그라운드 작업)과 다음 실행의 FAILED 처리가 같은 롤백 세션을 동시에 써서 SQLAlchemy 가 거부했습니다. 다시 시작을 정리가 끝난 뒤로 미뤘습니다(8.3절 B).
- **워커 역할이 풀릴 수 있었음:** 롤백 세션에서 `SET LOCAL ROLE` 은 SAVEPOINT 안에 걸려, 실행기의 `rollback`(SAVEPOINT 되돌리기)이 역할까지 되돌릴 수 있습니다. 역할을 건 직후 `commit`(SAVEPOINT 놓기)해 바깥 트랜잭션에 남기고, 끝날 때 역할이 그대로인지와 저장하는 순간의 역할을 단정합니다.
- **도는 중 STALE 로 바꾼 것이 지워짐:** 도구 안에서 실행을 STALE 로 바꾸기만 하면 실행기가 그래프 세션을 되돌릴 때 함께 지워집니다. 다른 트랜잭션이 커밋한 것처럼 바꾼 직후 `commit` 합니다.
- **이름·건수를 짐작함:** 설명 JSON 의 키 이름, T7 출력의 속성 이름, "위험 주문 7건"(실제로는 주문 3건의 상세 7행)을 확인 없이 적어 시험이 틀렸습니다. 실제 값으로 고쳤습니다.
- **측정용 Docker 마운트 경로가 깨짐:** 엔진 폴더 경로(한글 포함)를 셸 변수로 넘겼더니 글자가 깨져, Docker 가 깨진 이름의 빈 폴더 3개를 호스트에 새로 만들고 빈 폴더를 붙였습니다. 빈 폴더만 지웠고(원래 엔진 폴더는 그대로임을 확인), 경로를 셸을 거치지 않고 인자 목록으로 넘기게 고쳤습니다.
- **측정이 잠금을 기다리며 멈춤:** 21건을 실행마다 접속을 따로 열어 미리 되돌려 두었더니, 첫 실행의 시작 전이가 같은 지연의 다른 실행 행(다른 접속이 되돌려 놓고 커밋하지 않은 행)을 기다리며 멈췄습니다. 하나씩 돌릴 때는 접속 하나를 이어 쓰고, 동시에 돌릴 때는 서로 다른 지연의 실행만 고르게 고쳤습니다.
- **측정값을 그대로 믿을 뻔함:** 최악 경우가 동시 1건에서도 2.45GB 였는데, 접속 하나로 하나씩 돌린 값(1.94GB)과 달랐습니다. 살아 있는 저장소 수를 세고 참조를 따라가, 끝난 실행의 저장소가 접속에 묶여 남는다는 것을 찾았습니다(8.6절). 측정 장치가 접속을 열어 둔 탓이 섞인 값이라 표에 돌린 방법을 함께 적었습니다.

RLS 문맥 때(위 리뷰 항목)와 같은 종류의 빈 곳입니다. "세션 하나를 돌려쓴다"는 차이가 만드는 것을 그때 문맥 하나만 보고 닫은 탓입니다.

### 9.4 이 확인이 보지 않은 것·한계

- **지연 상세의 머리 칸은 시나리오 값이 아닙니다.** 지연 일수·계획/예상 입고·운송 수단과 "데이터 기준"은 빌린 실제 선적의 **지금** 일정과 화면용 DB 의 최근 수집 기준입니다(서버 응답 설계: 단계·입고일·지연 일수는 선적의 현재 값 — `delay_event_schemas.py`·`analysis_run_schemas.py`). 그래서 GS-05~GS-11 일곱 화면은 지연 0일에 "계획대로 입고"로, GS-02·GS-03 은 지연 +1일로 보입니다. 분석 결과 칸(재고 영향·위험 주문·대응안)만 시나리오 값입니다.
- **이름이 섞여 보입니다.** 표의 상품·주문 이름은 빌린 실제 행(예: A Glow Hydra Cream 50ml)이고, AI 설명 문장은 시나리오 세계의 코드(예: `CREAM20`)를 씁니다.
- **지연 감지·자동 시작·앱 실행기는 지나지 않았습니다.** 지연·실행 행은 직접 넣었고 그래프는 직접 불렀습니다. 그 구간은 8절 A·B 가 봅니다.
- **GS-09 R1·GS-10 v1 의 STALE 열은 저장 뒤 직접 채웠습니다.** 서버의 STALE 판정 자체는 8.5절 G(17/17)가 봅니다. 이 확인은 STALE 이 된 실행을 화면·API 가 어떻게 다루는지만 봅니다.
- **거부 중 본 것은 `ANALYSIS_STALE`(STALE·시간 경과)뿐입니다.** `OPERATING_RULE_CHANGED`·`EPISODE_CLOSED`·`FINAL_DECISION_EXISTS` 등의 화면은 보지 않았습니다. 팀원 초안(의견)은 팀원 계정이 필요해 보지 않았습니다.
- **설명은 mock 모델입니다.** 실제 모델 연결은 호출 자체는 되지만 지금 엔진 설명 프롬프트로는 검증 통과가 나오지 않아, 실제 모델로 하는 최종 확인은 데이터 팀의 설명 프롬프트 새 판 뒤로 미뤘습니다.
- **웹은 `29386f9` 기준입니다.** 그 뒤 지연 상세 화면이 바뀌면 9.2절 화면 대조를 다시 봐야 합니다.
- 씨앗 넣기·대조 스크립트와 결과 파일(대조표·화면 글자·스크린숏)은 데이터를 바꾸는 일회성 도구라 저장소에 넣지 않았습니다.

### 9.5 대조가 실패를 잡는지

- **API ↔ 정답:** GS-03·GS-05 의 확정 감소 기대값을 99 로 바꾸면 그 칸만 "다름"(23칸 중 같음 21·다름 1, 27칸 중 같음 25·다름 1).
- **화면 ↔ API:** GS-03 화면 글자 "커버 수량 200개"를 "199개"로 바꿔 넣으면 76칸(9.2절 표의 68 + 8) 중 그 칸만 "다름".
- **공급일:** 정답 기대값 한 칸(GS-03 현재 계획 유지 03-30 → 03-31)과 화면 글자 한 칸(예상 도착 03.17 → 03.18)을 바꾸면 각각 그 칸만 "다름"(27칸 중 26, 24칸 중 23).
- **v6 원문 대조·카드 재대조:** v6 값 두 칸(GS-03 KR 전체 회복, GS-08 현재 계획 유지 일부 확보)을 1 씩 올리면 231칸 중 그 두 칸만 "다름". 화면 값 한 칸(GS-08 현재 계획 유지 일부 확보 1 → 2)을 바꾸면 105칸 중 그 칸만 "다름".
- **성공 흐름 DB 확인:** 같은 확인을 선택하지 않은 데모 실행(`AN-260702-002`)에 돌리면 "FINALIZED 아님"으로 실패.

### 9.6 작업 중 실패와 원인

- **대조기가 처음엔 틀린 짝을 지음(4건):** SKU 가 여럿인 실행(GS-05)에서 첫 SKU 영향 행과 견줌, 주문 상세 2줄을 주문 2건으로 셈, 빈 값의 합을 0 으로 셈, 공급량의 짝을 SKU별 JSON 합으로 잡음(맞는 짝은 `securableQuantity` — 불가 대응안은 SKU별 공급량이 비어 있음). 기대값이 없는 참고 칸을 대조에 넣은 것도 있었습니다. "다름" 칸을 하나씩 원인까지 본 뒤 고쳤고, 고친 뒤 다름 0.
- **GS-10 넣기가 "검사 실패"로 되돌려짐:** 넣은 뒤 확인 조건이 v1 을 READY 로 기대했는데 정답은 STALE. 되돌리기 모드(dry-run)는 늘 되돌리므로 못 봤습니다. v1 기대 상태를 STALE 로 고쳐 다시 넣었습니다.
- **공급일 칸을 다른 필드와 이음(11-15 다시 검증하다 찾음):** 처음엔 정답의 공급일을 `skuResults` 의 SKU별 `supply_available_date` 와 이어, 그 값이 비는 11칸을 "응답에 없음(저장 계약상 비움)"으로 적고 공급일을 "API 에만 있음"으로 분류했습니다. DB 를 직접 읽어 보니 대응안 단위 공급일은 `expected_delivery_date`(응답 `expectedDeliveryDate`, 화면 "예상 도착")에 27칸 모두 정답과 같은 값으로 있었습니다. 이름이 "예상 배송일"이라 다른 값으로 넘겨짚은 것이 원인입니다(4.3절이 이미 적은 이름 차이). API·화면으로 다시 견줘 숫자를 고쳤습니다(같음 204 → 215, 화면 76 → 100).
- **확정 감소를 "화면에 보임"으로 잘못 분류(11-15 다시 검증하다 찾음):** 화면 글자에 "확정 감소 N개"가 있어 카드가 그리는 줄 알았는데, 웹의 대응안 변환에는 그 필드가 없고 그 문장은 AI 설명(mock 템플릿)의 대응안별 문장이었습니다. 화면 대조에서 그 8칸을 "카드"가 아니라 "AI 설명 문장"으로 따로 적고, 9.3절 분류를 "API 에만"으로 고쳤습니다. 처음 "다름" 1칸(GS-08 KR 확정 감소: 화면 없음 · API 0)도 같은 이유입니다 — 실행 가능이 아닌 대응안은 설명 문장에 확정 감소가 없어 "화면 표시 안 함"으로 분류했습니다(GS-07·GS-08 각 1).
