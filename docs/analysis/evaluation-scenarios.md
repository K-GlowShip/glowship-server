## 4. 발견 (엔진·다른 담당 몫, 결정 대기)

### 4.1 설명 검증기가 구분자 없는 SKU 코드 안의 숫자를 수치로 센다 — 평가 fixture 설명이 실패 (11-07 범위 바로잡음, 11-11 해결)

- **현상:** 엔진을 직접 불러도(서버 감싸기 없이) GS-02·03·07·08·09A·09B·10·11 의 mock 설명이 3번 모두 `VALUE_MISMATCH@risk_summary#s2` 로 실패합니다. GS-05(SKU `X`·`Y`)만 통과합니다.
- **원인:** `explain/textcheck.tokens` 가 "SKU별 지연 증분은 CREAM20 100개입니다" 에서 숫자를 `[20, 100]` 으로 셉니다. 문장이 인용한 값은 `[100]` 하나라 다중집합이 달라집니다(`validator.py` 의 1:1 대응 규칙). `CREAM20` 은 코드 토큰으로도 잡히지 않습니다. 코드 토큰 규칙(`textcheck.py` 12행 `CODE`)은 `-`·`_` 로 이어진 대문자 코드만 코드로 빼내므로, `SKU-005 31개` 는 `[31]` 로 맞게 셉니다. 숫자를 잘못 세는 것은 `CREAM20`·`SKU005` 처럼 구분자 없이 영문 뒤에 숫자가 붙은 코드뿐입니다.
- **영향:** 엔진 평가 fixture(GLOW-50)의 SKU 코드(`CREAM20`·`TONER50` …)로 만든 설명이 엔진 자기 검증기에 걸려, 평가 시나리오에서 설명 통과를 확인할 수 없습니다. 실제 DB 의 SKU 코드(`SKU-001` 모양, 구분자 있음)는 해당하지 않습니다 — overlay 실행 13건이 `SKU-005`·`SKU-026` 같은 코드로 설명 PASSED 로 저장돼 있습니다. 운영 SKU 코드가 구분자 없는 모양이면 같은 실패가 납니다.
- **바로잡음(11-07):** 11-06 판은 "실제 DB SKU 코드도 해당, 운영에서 설명이 항상 실패"라고 적었습니다. `CREAM20` 만 토크나이저에 넣어 보고 `SKU-001` 모양은 넣어 보지 않은 채 미루어 적은 것이었습니다. GLOW-127 후속(overlay 회귀) 준비 중에 저장된 PASSED 설명을 보고 확인했습니다.
- **서버 쪽 처리(11-06~11-10):** 설명 실패 흐름(#28 `explanation_failure`: FAILED·VALIDATING_OUTPUT·시도 3·소진)은 맞게 돌았습니다. 통과 기대 시험을 `strict xfail` 로, 원인과 실패 모양을 따로 고정해 두었습니다.

- **평가 시나리오 10건을 DB 에 넣지 않은 이유:** 시나리오는 DB 데이터가 아니라 엔진 fixture 가 손으로 만든 스냅샷입니다. DB 에 넣으려면 스냅샷을 표로 되돌리는 변환을 새로 만들어야 하고, 그 변환이 틀리면 시험이 변환을 검증하게 됩니다. 그래서 DB 를 지나는 길(조회 도구 T1~T5·T8, 엔진 입력, 저장)은 확정 DB 의 정답 실행 21건으로, 시나리오의 숫자는 그래프로 나눠 봅니다.

- **장치의 세션과 시간 제한:** 장치는 롤백 세션 하나를 실행기에 돌려주되, 세션을 열 때 RLS 문맥을 비우고 세션이 끝날 때 커밋 안 한 것을 버립니다(앱은 세션마다 새 접속이고, 닫으며 버림). 실행기의 시간 제한(분석·저장)은 꺼 둡니다. 제한에 걸려 DB 질의가 도중에 취소되면 접속이 무효가 되는데, 앱은 그 접속을 버리고 새로 열지만 장치는 시험 트랜잭션 전체가 그 접속 하나라 이어 갈 수 없기 때문입니다. 정답 대조는 PC 속도와 상관없어야 하고, 제한에 걸린 뒤의 동작(다시 저장·`FAILED`)은 실행기 시험이 봅니다.

### 8.4 GS-09·GS-10 의 서버 쪽을 어떻게 다뤘나

- **GS-09(STALE 재판정·서명 재계산):** 시나리오 숫자 그대로는 서버에 넣지 않았습니다(시나리오가 DB 에 없음). 같은 규칙("서명이 같으면 유지")을 확정 데이터의 STALE 열로 견줍니다(8.5절). 처음에는 서버에 판정 서명 재계산기가 없어 정답과 다른 8건을 strict xfail 로 두었고, #116 으로 재계산기가 연결된 뒤 다시 대조했습니다. 정답표의 "최종 선택 거부"는 판단 쪽 시험(`test_selection_policy`·`test_final_decision_service`)이 봅니다.
- **GS-10(지연 감지 → 후속 실행 생성):** 생성과 이전 실행 STALE 은 `test_auto_run_sql.py`, 수집 → 자동 시작 넘김은 `test_manual_sync_start_runs.py` 가 이미 봅니다. 여기서는 그 조각들을 실제 STALE 판정·실제 묶음으로 한 번 이어 붙였습니다(B5):
  1. 새 지연 선적 수집 → v1 `AUTO/EPISODE_STARTED`·`DETECTED`(입력 순번 = 그 수집) → 실제 경로로 끝 상태 저장(저장 뒤 데이터 버전 5건)
  2. 같은 선적의 예상 입고일을 10일 늦춰 다시 수집 → v1 `STALE`·`DELAY_SCHEDULE_CHANGED`(감지 순번 = 그 수집, 현재 버전 아님, 결과는 보존)
  3. v2 `AUTO/SCHEDULE_WORSENED`·부모 = v1·버전 2·입력 순번 = 그 수집·`DETECTED`
  4. v2 실제 경로로 끝 상태 저장(저장 뒤 데이터 버전 5건), v1 은 그대로 STALE
- 새 선적은 지연 증분이 없어 두 실행 모두 `NO_RISK` 로 끝납니다. 시험은 두 실행의 끝 상태를 `NO_RISK` 로 단정하고 흐름·상태·연결을 봅니다. 대응안 숫자는 보지 않습니다. GS-10 의 숫자(소진일 03-11 등)는 C 갈래와 1단계가 봅니다.
- 데이터 버전은 저장 뒤 건수만 봅니다(도메인 5개). 자동 실행은 만들 때가 아니라 결과를 저장할 때 기록합니다(#120). 만든 직후 0건인 것은 `test_auto_run_sql.py` 가 봅니다.

- **#119 전 코드는 2GB 에서 저장 직후 재판정의 재계산이 2번이면 죽습니다.** 재계산기(`EngineSignatureRecalculator`)가 트랜잭션 하나 동안 읽은 순번 저장소를 모두 들고 있었기 때문입니다. 재계산 한 번 뒤 RSS 가 1.47GB(실행 입력 저장소 = 캐시, 새 순번 저장소 하나, 그 밖 0.16GB)이고, 다음 순번 저장소를 읽는 동안 2GB 를 넘습니다. 첫 재계산까지는 두 실행 모두 끝났습니다(재계산 1번은 넘지 않음).
- **"순번 저장소를 하나만 듦"**은 측정 스크립트가 재계산이 끝날 때마다 재계산기가 든 저장소를 비운 것입니다(운영 코드는 그대로). 같은 방식의 수정(마지막으로 읽은 순번 하나만 듦)이 #119 로 들어왔습니다(11-12 머지). 머지된 코드 자체를 2GB 에서 재지는 않았고, 그 PR 의 리뷰가 제한 없는 PC 에서 14개 순번을 돌려 최고 1.48GB 를 확인했습니다.
- **메모리가 해결돼도 시간은 남습니다.** 재계산 한 번은 저장소 한 번 읽기(CPU 1 에서 약 12초)이고, 저장 트랜잭션과 그 실행의 행 잠금(L2)이 "관련 수집 수 × 약 12초" 동안 이어집니다(2번 32초, 14번 187초). 그동안 같은 실행을 판정하려는 수집은 고객사 잠금(L1)을 쥔 채 기다립니다. 분석(새로 읽는 실행 8.5~19초)에 재계산 1번(12~14초)만 더해져도 30초 안팎입니다.
- **앱에서 언제 생기나:** 저장 직후 재판정은 실행의 입력 순번 뒤에 적용된 수집을 모두 봅니다. 수집 직후 바로 분석하면 그 사이 수집이 0~1번이라 재계산도 0~1번입니다. 2번 이상이 되는 것은 ① 분석하는 동안 수집이 잇달아 들어올 때(동기화를 연달아 누름, 데모의 "다음 날로") ② 실행이 `DETECTED` 로 오래 남았다가 시작될 때(자동 시작을 끈 채 수집이 쌓인 뒤 켜거나, 서버 시작 정리가 다시 시작시킴)입니다. ②는 자동 시작을 처음 켜는 날 그대로 생길 수 있습니다.
- `/health` 는 재계산 중 최대 0.27~0.47초였습니다.
- **재지 않은 것:** 수집 재판정과 다른 실행의 분석이 같은 프로세스에서 겹칠 때(저장소가 실행 입력 + 새 순번 + 분석 중인 실행 것으로 3개가 될 수 있음), 동시 실행 2건 이상에서의 재계산, dev 서버 실측.

### 8.8 작업 중 실패와 원인 (2단계)

- **주입 없는 대조에서 의존 범위까지 견주려 함:** RT-2 를 주입 없이 돌린 결과(READY)를 정답(설명 실패)과 의존 범위까지 견줬더니 달랐습니다. 설명 실패 저장은 의존 범위를 남기지 않습니다(정상 완료 값은 쓰지 않음, `result-save.md`). 판정 서명과 결과 행만 견주게 고쳤습니다.
- **시작 정리 시험이 세션을 동시에 씀:** 정리가 다시 시작시킨 실행(백그라운드 작업)과 다음 실행의 FAILED 처리가 같은 롤백 세션을 동시에 써서 SQLAlchemy 가 거부했습니다. 다시 시작을 정리가 끝난 뒤로 미뤘습니다(8.3절 B).
- **워커 역할이 풀릴 수 있었음:** 롤백 세션에서 `SET LOCAL ROLE` 은 SAVEPOINT 안에 걸려, 실행기의 `rollback`(SAVEPOINT 되돌리기)이 역할까지 되돌릴 수 있습니다. 역할을 건 직후 `commit`(SAVEPOINT 놓기)해 바깥 트랜잭션에 남기고, 끝날 때 역할이 그대로인지와 저장하는 순간의 역할을 단정합니다.
- **도는 중 STALE 로 바꾼 것이 지워짐:** 도구 안에서 실행을 STALE 로 바꾸기만 하면 실행기가 그래프 세션을 되돌릴 때 함께 지워집니다. 다른 트랜잭션이 커밋한 것처럼 바꾼 직후 `commit` 합니다.
- **이름·건수를 짐작함:** 설명 JSON 의 키 이름, T7 출력의 속성 이름, "위험 주문 7건"(실제로는 주문 3건의 상세 7행)을 확인 없이 적어 시험이 틀렸습니다. 실제 값으로 고쳤습니다.
- **측정용 Docker 마운트 경로가 깨짐:** 엔진 폴더 경로(한글 포함)를 셸 변수로 넘겼더니 글자가 깨져, Docker 가 깨진 이름의 빈 폴더 3개를 호스트에 새로 만들고 빈 폴더를 붙였습니다. 빈 폴더만 지웠고(원래 엔진 폴더는 그대로임을 확인), 경로를 셸을 거치지 않고 인자 목록으로 넘기게 고쳤습니다.
- **측정이 잠금을 기다리며 멈춤:** 21건을 실행마다 접속을 따로 열어 미리 되돌려 두었더니, 첫 실행의 시작 전이가 같은 지연의 다른 실행 행(다른 접속이 되돌려 놓고 커밋하지 않은 행)을 기다리며 멈췄습니다. 하나씩 돌릴 때는 접속 하나를 이어 쓰고, 동시에 돌릴 때는 서로 다른 지연의 실행만 고르게 고쳤습니다.
- **측정값을 그대로 믿을 뻔함:** 최악 경우가 동시 1건에서도 2.45GB 였는데, 접속 하나로 하나씩 돌린 값(1.94GB)과 달랐습니다. 살아 있는 저장소 수를 세고 참조를 따라가, 끝난 실행의 저장소가 접속에 묶여 남는다는 것을 찾았습니다(8.6절). 측정 장치가 접속을 열어 둔 탓이 섞인 값이라 표에 돌린 방법을 함께 적었습니다.
- **변이 스크립트를 고치다 깨뜨림:** M11·M13 을 넣으며 `\n` 표기가 실제 줄바꿈으로 들어가 변이 스크립트가 문법 오류로 돌지 않았습니다(뒤이은 전체 시험만 돌고 변이는 0개). 결과 파일을 보고 알아채 고친 뒤 다시 돌렸습니다. 고친 직후 스크립트를 한 번 컴파일해 보지 않은 탓입니다.
- **재측정의 수집 재판정 장면이 빈 결과를 냄:** 측정 스크립트가 워커 역할만 걸고 고객사 RLS 문맥(`set_rls_context`)을 넣지 않아, 판정 대상 실행이 보이지 않았습니다(재계산 0번·0초). 0초라는 값이 이상해 원인을 찾았고, 수집 트랜잭션처럼 문맥을 넣어 다시 쟀습니다. 앱 실행기는 세션을 열 때 문맥을 넣는데, 판정 서비스를 직접 부르면서 그 단계를 빠뜨린 것입니다.
- **독립 리뷰에서 나온 것(push 전, 11-12):** 결론을 주지 않고 코드만 넘긴 리뷰가 아래를 찾았고, 모두 고쳤습니다.
  - 장치가 세션 하나를 돌려써서, 앞에서 넣은 RLS 문맥이 남아 실행기가 저장 세션에 문맥을 넣는 줄을 지워도 시험이 통과했습니다(변이로 확인). 세션을 열 때마다 문맥을 비우게 고쳤고, 이제 그 변이를 6개 시험이 잡습니다(8.7절 M15). 그래프 세션 쪽 같은 줄(M14)은 지워도 통과하는데, 앱에서도 엔진 입력·저장소 읽기·실행 상태 조회가 같은 세션에 문맥을 넣기 때문입니다.
  - 한 흐름 시험(B5)의 "보류면 데이터 버전 0건" 기대값이 그때 코드(#120 전)에서는 틀렸습니다(자동 실행이 만들 때 5건을 기록해 보류로 끝나도 5건). 두 실행의 끝 상태를 `NO_RISK` 로 단정하고 그 갈래를 없앴습니다.
  - 추적 시험 이름이 "코드를 가린다"였지만 실제로 보는 것은 "기록에 코드 원문이 없다"였습니다(가리는 규칙을 지워도 통과, 변이로 확인). 이름과 설명을 고쳤습니다.
  - 저장소 파일에 저장소 밖 기록의 번호를 적었던 것, 같은 시간을 절마다 다르게 적은 것, 표의 55.3초를 정리에서 뺀 것을 고쳤습니다.
- **검증하는 사이 develop 이 다섯 번 움직임(11-12):** push 전 검증을 도는 동안 #119·#120·#121·#124·#125 가 머지됐습니다. 병합해 보니 충돌은 없었지만, 앱 재계산기가 저장소를 하나만 들게 되어 시험의 우회가 필요 없어졌고, 앱 실행기에 세션을 바꿔 끼우는 인자가 생겨 장치가 앱 조립을 따라 적지 않고 그대로 부르게 고쳤습니다. 검증은 병합한 위에서 처음부터 다시 했습니다.
- **문서 숫자를 원본에서 다시 계산해 대조(push 전):** 8절의 숫자 24개를 측정·시험 결과 파일에서 다시 계산해 견줬더니 한 곳이 달랐습니다(재계산 한 번 뒤 RSS 를 1.46GB 로 적음, 원본 1,465MB = 1.47GB). 눈으로 읽을 때는 지나쳤던 값입니다.
- **장치가 세션 닫기를 흉내 내지 않았음(11-12, 머지 뒤 찾음):** 실행 시간 제한이 들어올 것에 대비해 저장 제한을 3초로 걸고 돌려 보니, 첫 저장이 취소된 뒤 다시 저장하는 단계에서 장치가 `PendingRollbackError` 로 멈췄습니다. 세션이 예외로 끝날 때 되돌리게 고쳐도 같았습니다. 취소가 DB 질의 도중에 걸려 접속 자체가 무효가 됐고, 장치는 시험 트랜잭션 전체가 그 접속 하나라 되살릴 수 없었습니다. 그래서 장치는 시간 제한을 끕니다(8.1절). 원인을 찾다가 더 넓은 빈 곳도 보였습니다. 앱은 세션을 닫으며 커밋 안 한 것을 버리는데 장치는 세션 하나를 돌려써 버리지 않았고, 그래서 커밋이 빠지거나 저장이 도중에 실패해도 쓴 것이 남았습니다. 세션이 끝날 때마다 되돌리게 고치고 장치 시험 1건을 더했습니다. RLS 문맥 때(위 리뷰 항목)와 같은 종류의 빈 곳입니다. "세션 하나를 돌려쓴다"는 차이가 만드는 것을 그때 문맥 하나만 보고 닫은 탓입니다.
- **재측정이 내 다른 시험과 겹쳐 교착(11-12):** #131 머지 뒤 재측정 첫 시도가 첫 장면에서 `deadlock detected` 로 멈췄습니다. 앞서 멈춘 줄 알았던 내 검증 스크립트(백그라운드 bash)가 실제로는 계속 돌아, 같은 DB 에서 정답 실행 행을 되돌리는 시험과 측정이 같은 행을 잡았습니다. 멈추기 도구가 "멈춤"을 돌려줬지만 bash 는 남았고, 저는 python 자식 일부만 확인했습니다. 남은 프로세스를 모두 끄고 다른 접속 0개를 확인한 뒤 처음부터 다시 쟀고, 측정 스크립트가 시작 전에 다른 접속 수를 확인하게 했습니다. 실패한 시도의 값은 쓰지 않았습니다.
