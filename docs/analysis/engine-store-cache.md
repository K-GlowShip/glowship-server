# 엔진 저장소 캐시 (고객사·입력 순번마다 한 번 읽기)

- 대상: `app/modules/delay_analysis/infrastructure/engine/engine_store_cache.py`(캐시), `engine_input_store.py`(넣지 않는 색인), `engine_input.py`(`build_engine_input`이 캐시를 거침), 설정 `ENGINE_STORE_CACHE_MAX_ENTRIES`
- 시험: `tests/modules/delay_analysis/test_engine_store_cache.py`, 시험마다 캐시 비우기 `tests/modules/delay_analysis/conftest.py`
- 티켓: GLOW-125, 이슈 #60(PR #53 후속)
- 전제: 분석 자동 시작(이슈 #51)은 API 서버 프로세스 안의 asyncio 작업으로 돌고, 서버 프로세스는 1개, 동시 실행은 기본 4개입니다. 한 SHIPMENT 수집이 만든 같은 고객사·같은 입력 순번 AUTO 실행들이 동시에 시작합니다.

## 1. 왜 필요한가
- `build_engine_input`은 실행마다 `load_company_engine_store`로 한 고객사 저장소 전체를 읽습니다(`engine-input-store.md`).
- 읽는 데 오래 걸리고 저장소가 큽니다(아래 표, 11-08 개발 DB, `tracemalloc`으로 잰 파이썬 객체 크기).
- 같은 고객사·같은 입력 순번 실행(한 수집의 AUTO 실행 여럿, 수집 사이의 재분석)은 똑같은 저장소를 읽습니다.

| 고객사 | 주문 | 주문 상세 | 변경 기록 | 재고 행 | 저장소 크기 | 읽는 동안 최대 |
| --- | --- | --- | --- | --- | --- | --- |
| A_BEAUTY | 106,983 | 160,411 | 265,692 | 36,036 | 약 490MB | 약 740MB |
| B_COSMETICS | 64,905 | 97,279 | 166,756 | 24,024 | 약 310MB | 약 460MB |

읽는 시간은 `engine-input-store.md` 4절 측정으로 A_BEAUTY 약 9.5초입니다(`tracemalloc`을 켜면 몇 배 느려짐).

## 2. 열쇠: (고객사, 입력 순번)
저장소 = 입력 순번으로 거르는 표 + 거르지 않는 표입니다(`engine-input-store.md` 2절).

| 같은 열쇠에서 나중에 다시 읽으면 바뀌는 것 | 결과에 닿는가 |
| --- | --- |
| 순번 없는 수집 행(`data_sync_runs`의 RUNNING·FAILED, `applied_seq IS NULL`도 읽음) | 닿는 곳은 엔진 `store.order_collection_due`(STALE 재계산 `knowledge_t` 경로, 서버 코드는 `knowledge_t`를 쓰지 않음)와 `snap["data_versions"]`(판정 서명에 들어가지 않음, API 17 데이터 버전은 DB에서 따로 읽음)뿐. 입력 순번 확인·재고 as-of·기준일 D·T4·T8은 순번 있는 행만 봅니다 |
| 뒤 수집이 적용된 뒤의 현재 상태 표(주문·주문 상세·선적 등)와 변경 기록 | 저장소가 일부러 거르지 않는 표입니다(#36 결정). 뒤 수집이 적용되면 `applied_seq`가 올라 그 뒤에 만든 실행은 새 입력 순번이라 새로 읽습니다. 옛 입력 순번을 다시 읽는 것은 같은 순번 실행이 늦게 시작할 때뿐이고, 그때 캐시는 **먼저 읽은 것**을 줍니다. 그쪽이 그 입력 순번 시점에 더 가깝습니다. 서버 재시작 뒤 다시 시작한 실행은 캐시가 비어 있어 캐시가 없을 때처럼 새로 읽습니다 |

- 열쇠에 `max(applied_seq)`를 붙이는 안(`engine-input.md` 7절의 옛 제안)은 쓰지 않습니다. 순번 없는 수집 행은 `max(applied_seq)`를 바꾸지 않아 잡지 못하고, 잡는 것은 "뒤 수집 뒤에 옛 순번을 다시 읽기"인데 그러면 뒤 수집의 현재 상태가 섞여 "같은 입력 순번 = 같은 결과"에서 오히려 멀어집니다.
- 서버의 STALE 판정(`application/stale/`)은 엔진 저장소를 읽지 않고 SQL로 판정합니다. 그래서 변경 기록이 늘어도 캐시와 상관없습니다.
- 고객사 ID는 `uuid.UUID`로 맞춰 열쇠로 씁니다(문자열로 불러도 같은 열쇠).
- 캐시는 지연 이벤트를 찾은 뒤(`_run_input`, 실행의 고객사 RLS로 조회) 거칩니다. 고객사가 보이지 않는 세션은 그 전에 `LookupError`로 멈추므로, 다른 세션이 읽어 둔 저장소를 받지 않습니다.

## 3. 같은 열쇠를 동시에 처음 읽을 때: 열쇠별 `asyncio.Lock`
- 이미 있는 열쇠는 잠금 없이 바로 돌려줍니다(가장 오래 안 쓴 순서만 갱신).
- 없는 열쇠는 열쇠별 잠금을 잡고 한 번 더 확인한 뒤 읽습니다. 기다린 호출은 첫 호출이 읽은 저장소를 받습니다(`coalesced`).
- **Future 공유 대신 잠금을 쓴 이유:** 첫 호출이 읽다가 취소되면(서버 종료 유예) 잠금은 풀리고 다음 호출이 **자기 세션으로** 읽습니다. Future 공유는 첫 호출의 세션으로 돌던 읽기를 모두가 기다려서, 그 세션이 닫히면 모두 실패하거나 별도 장치가 더 필요합니다.
- **실행기가 고객사별로 차례로 돌리는 안과 비교:** 그 안은 입력 순번이 달라도 저장소 읽기·스냅샷·계산을 모두 줄 세우고, 캐시를 쓰는 다른 곳(재분석, 시험)에는 합치기가 없습니다. 열쇠별 잠금은 없는 열쇠일 때만, 같은 열쇠끼리만 기다립니다. 그래서 실행기에는 따로 둘 것이 없습니다.
- 읽다가 예외가 나면 넣지 않습니다. 다음 호출이 다시 읽습니다(실패를 캐시하지 않음).
- 캐시 자료구조는 이벤트 루프 스레드에서만 다룹니다(읽기·엔진 계산만 스레드). 그래서 스레드 잠금이 필요 없습니다.
- 열쇠별 잠금은 쓰는 호출이 없어지면 지웁니다(잠금이 쌓이지 않음).

## 4. 함께 읽는 저장소는 바뀌면 안 됨: 넣지 않는 색인
- 캐시 뒤에는 **같은 저장소 객체를 여러 실행이 스레드에서 함께 읽습니다**(`asyncio.to_thread`).
- 엔진 `Store.__init__`은 색인 6개를 `defaultdict`로 만듭니다: `lines`·`ship_lines`·`snaps`·`dcr_by_day`(목록), `demand`·`demand_ch`(정수).
- 엔진 `snapshot.build`는 이 색인을 대괄호로 읽습니다: `mu()`의 `store.demand`·`demand_ch`, `store.lines`·`store.ship_lines`, `store.snapshot_at`의 `store.snaps`. 없는 열쇠를 읽으면 `defaultdict`가 **열쇠를 넣습니다**. STALE 재계산 경로는 `store.demand.items()`를 돕니다.
- 그대로 두면 읽기가 쓰기가 되어, 한 스레드가 항목을 도는 동안 다른 스레드가 넣으면 `RuntimeError: dictionary changed size during iteration`가 나고 저장소가 실행마다 조금씩 바뀝니다.
- 엔진 코드는 해시로 고정돼 고칠 수 없습니다. 그래서 서버 `CompanyEngineStore.__init__`이 색인을 다 만든 **뒤** 6개를 `NoInsertDefaultDict`로 바꿉니다(`freeze_default_dicts`). 없는 열쇠를 읽으면 `0`·`[]`를 돌려주기만 하고 넣지 않습니다.
- `dict`를 상속해 내용이 같으면 `defaultdict`와 `==`로 같습니다. 그래서 엔진이 직접 만든 Store와 속성을 하나씩 대조하는 시험(`test_company_store_equals_engine_store_golden`)이 그대로 성립합니다. 속성 이름·순서는 그대로이고 새 속성은 더하지 않습니다.
- 엔진은 빈 목록을 돌려받아도 거기에 넣지 않습니다(돌기·정렬만). 돌려주는 빈 목록은 매번 새것이라 고쳐도 사전에 남지 않습니다.
- 서버 쪽 읽는 곳도 읽기만 합니다: 조회 도구 T4(`demand_ch.get`)·T8(`store.t`·`lead_days`), 기준일 D(`store.runs`·`inv.values()`·`runs_until`), 설명 생성(`store.ships.get`). T6·T7은 `snap`만 읽습니다.
- 캐시를 거치지 않는 곳(데모 시드 `scripts/seed_demo_runs.py`, 수집 규칙 시험)도 같은 저장소 클래스를 쓰므로 같은 색인을 받습니다. 동작은 같습니다.

## 5. 메모리와 설정
- 상한은 **항목 수**입니다: `ENGINE_STORE_CACHE_MAX_ENTRIES`, 기본 **2**(2026 H1 고객사 수), 0이면 캐시를 끕니다(사용자 결정 11-08). 넘으면 가장 오래 안 쓴 것부터 버립니다.
- 바이트로 재려면 저장소마다 직렬화(수 초)나 추정식이 필요한데, 고객사 수가 작고 고객사별 크기가 안정적이라 항목 수가 단순합니다. **고객사가 늘면 고객사 수만큼 올립니다.**
- 최악 상주 = 상한 × 저장소 크기 + 버려졌지만 아직 도는 실행이 `EngineInput.store`로 잡고 있는 저장소. 캐시가 없을 때도 동시 실행 4개면 저장소 4개가 살아 있었으므로, 캐시는 같은 열쇠를 합쳐 메모리를 줄이는 쪽입니다.
- **메모리가 작은 서버(예: 메모리 2GB):** 상한을 **1**로 둡니다(#89 리뷰). 저장소 하나와 읽는 동안의 중간값, 엔진 계산이 함께 올라가기 때문입니다. **0보다 1이 낫습니다.** 0이면 같은 열쇠 동시 읽기 합치기도 꺼져, 같은 고객사 실행이 동시에 시작할 때 실행 수만큼 저장소를 따로 읽어 메모리가 오히려 늘어납니다.
- **DB를 다시 적재하면 서버를 다시 시작합니다**(#89 리뷰). 확정 묶음으로 다시 적재하면 같은 (고객사 UUID, 입력 순번)이 다시 생겨, 서버를 띄운 채면 캐시가 다시 적재하기 전의 저장소를 줍니다. 서버를 다시 시작하거나 `engine_store_cache().clear()`로 비웁니다.
- 서버가 다시 시작되면 비어 있습니다(받아들임). `engine_store_cache().clear()`로 비울 수 있습니다(시험 사이, 수집 밖에서 업무 데이터를 직접 고쳤을 때). 비우는 관리 API는 없습니다.
- 관측: 새로 읽을 때마다 INFO 로그 "엔진 저장소 읽음: 고객사 … 입력 순번 …, N초", 버릴 때 "엔진 저장소 캐시에서 버림". `engine_store_cache().stats()` = `hits`·`misses`·`coalesced`·`evictions`·`size`. 자동 시작의 "같은 고객사 AUTO 3건 동시 → 저장소 로드 1회" 확인은 `misses == 1`·`coalesced == 2`로 봅니다.

## 6. 쓰는 곳과 그대로 둔 것
- `build_engine_input`이 `get_company_engine_store(session, company_id, input_seq)`를 부릅니다. 바뀐 줄은 그 한 줄입니다.
- `load_company_engine_store`는 모양·동작을 그대로 둡니다. 데모 시드가 직접 부르고, 캐시는 이 함수를 감쌉니다.
- 엔진 코드, 조회 도구, 도구 문맥은 고치지 않았습니다. 도구 문맥 주석의 "저장소 읽기 고객사당 약 9.5초"는 새로 읽을 때 그대로 맞습니다.

## 8. 작업 중 실패와 결정
- **계획의 근거 문장이 넓었습니다.** 계획(11-08)은 "같은 열쇠에서 저장소 내용이 바뀌는 것은 순번 없는 수집 행뿐"이라고 적었습니다. 문서를 쓰며 `engine-input-store.md` 2절을 다시 보니, 현재 상태 표와 변경 기록도 입력 순번으로 거르지 않아 뒤 수집 뒤에는 같은 열쇠라도 다시 읽은 내용이 바뀝니다. 결론(열쇠)은 그대로입니다. 그 경우 캐시가 먼저 읽은 것을 주는 쪽이 입력 순번 시점에 더 가깝고, 서버 STALE 판정은 저장소를 읽지 않기 때문입니다. 2절 표에 두 경우를 나눠 적었습니다.
- `engine-input-store.md` 4절의 옛 후보(PR #36 리뷰 제안)는 "입력 순번이 같아도 STALE 판정용 변경 기록이 늘 수 있어 마지막 적용 순번을 열쇠에 넣는다"였습니다. 서버 STALE 판정(`application/stale/`)이 엔진 저장소를 쓰지 않는 것을 확인해 이 이유는 없어졌고, 열쇠에서 뺐습니다.

## 9. 남은 일
- 서버가 STALE 재계산에 `knowledge_t`를 쓰게 되면, 순번 없는 ORDER 수집 행이 `order_collection_due`를 바꿉니다. 그 기능이 캐시 저장소를 쓸지 새로 읽을지 그때 정합니다.
- 서버 프로세스가 2개 이상이 되면 프로세스마다 캐시가 하나씩 생깁니다(상한 × 프로세스 수).
